# Private Cloud external PostgreSQL/S3 (new-install source and bundle evaluation)

This local-source profile and newly wired bundle Operator route are **single-Runtime, fresh-install evaluation paths**, not an upgrade, production-supported storage mode, or multi-Runtime/HA claim. It places control-plane data (including browser sessions and OIDC login state) in an operator-managed control PostgreSQL database and Runtime Unit/Session/Queue state in a separate operator-managed Runtime PostgreSQL database, with object-backed attachment/artifact bytes in S3-compatible storage. This does not include local-only trace/profile/export outputs. Neither `runtime-host` nor `runtime-ingress` mounts an authoritative application-data volume.

The new-install PG/S3 topology starts from `compose.postgres-s3-base.yaml` and then `compose.storage-postgres-s3.yaml`; it does **not** inherit `compose.yaml`, `control-postgres`, `init-volumes`, `tenant-data`, or any NFS server/network/backing volume. The old `compose.yaml` and storage overlays remain in bundles **only** for already installed legacy projects; new local-volume/NFS installations are refused, not converted. Never mix the PG/S3 root with legacy storage overlays. Named `host-secrets`, `gateway-secrets`, `runtime-storage-secrets`, and `gateway-storage-secrets` volumes are restricted, rebuildable projections of host secret files; they are not database or object authority. **These host files are evaluation-only secret sources**, not the target production Private Cloud `SecretResolver` with workload identity, rotation, audit, availability and restore contract.

This does **not** establish that every Private Cloud component is free of local authority. Optional bundled identity has separate state, Docker/Compose metadata and secret source files remain host-local, and JSONL-dependent or other legacy capabilities still require audit. The published signed beta installer still defaults to `local-volume`; the bundle route described here exists in local source, not in an accepted/certified release asset.

## Preconditions

1. Provision an **existing, empty control PostgreSQL database** reachable from the Gateway and the one-shot migration job. Compose will not create the server or database. Create two distinct login roles and credentials:
   - a migration owner that owns the database/schema and can run all control-plane migrations;
   - an existing Gateway writer without database/schema creation, table ownership, or migration authority. The one-shot owner migration job grants this role the steady-state table DML and sequence usage/select privileges after every schema migration; it does not create roles or revoke excess pre-existing grants.

   Both URLs must select the same pre-created database. Use PostgreSQL TLS appropriate to the environment. The migration job first connects to that database and fails before reading/applying migrations if it is absent or unreachable. Migration checksum/version failures are fatal; the Gateway also refuses to start against a missing, stale, or modified schema. Do not grant the migration owner credential to the Gateway.

2. Provision a **separate Runtime PostgreSQL database** reachable by the Runtime, Gateway, and Runtime migration job. Create three distinct login roles in advance: migration owner (owns this database and `public` schema), Runtime DML writer, and Gateway read-only reader. Neither workload role may have DDL, table ownership, or elevated privileges. Do not reuse the control database or its roles.

3. Provision a **new, dedicated, completely empty** private S3-compatible bucket, endpoint, region, and **two distinct S3 identities**: a one-shot bootstrap identity with bucket-wide `ListObjectsV2`/`ListObjectVersions` and conditional `PutObject` (`If-None-Match: *`) for the installation marker, and a steady-state Runtime identity with object read/write/delete for application objects plus `GetObject` for both `_kala/installation-claim.json` and `_kala/recovery-checkpoint.json`, but an explicit provider-enforced **deny of `PutObject` and `DeleteObject` on both `_kala/installation-claim.json` and `_kala/recovery-checkpoint.json`**. Do not give the bootstrap key to either workload or permit the Runtime key to modify either reserved object. The endpoint must implement `ListObjectsV2` and `ListObjectVersions`; a bucket with old versions or delete markers is not empty. Both PostgreSQL databases must also have no existing application schemas/objects before the claim job runs. Ensure the Runtime has network access, correct CA trust, and a durable object backup/restore plan. No PostgreSQL server or object store is bundled.

4. Use Docker Compose **2.24 or newer** (`!override` is required). Configure an externally managed OIDC issuer/client reachable from the Gateway and operator, with a correctly registered callback; PG/S3 preflight checks OIDC discovery but does not require the repository's local shared Identity Compose project. Install as a **new Compose project** with new external databases and bucket. There is no supported migration or rollback from `local-volume` or experimental NFS. Do not change the profile of a running installation in place. Existing legacy volumes are deliberately left untouched; after a successful cutover and retention review, their disposition remains an operator action.

5. In `deploy/private-cloud/.secrets` (or `KALA_SECRETS_DIR`), create owner-readable, group/other-inaccessible files:
   - `control_postgres_migration_owner_url` and `control_postgres_writer_url`;
   - `runtime_postgres_owner_url`, `runtime_postgres_writer_url`, and `runtime_postgres_reader_url`;
   - `runtime_s3_access_key_id` and `runtime_s3_secret_access_key` (marker read-only, application objects writable);
   - `installation_claim_s3_access_key_id` and `installation_claim_s3_secret_access_key` (one-shot bootstrap claim, never projected to workloads);
   - `runtime_state_master_key`, containing exactly 32 raw random bytes.

   Each PostgreSQL file contains a full URL. Preserve and securely back up the Runtime state key; losing it makes encrypted Runtime state unreadable. Never place database URLs, passwords, S3 credentials, or this key in `deployment.env`, Compose environment values, command arguments, or Git. The legacy `control_postgres_password` file is not required by this profile.

6. Put only non-secret profile selection in the ignored `deployment.env`, alongside existing OIDC and immutable image settings:

   ```dotenv
   KALA_PROFILE=postgres-s3
   COMPOSE_PROJECT_NAME=kala-private-cloud-pg-s3-eval
   KALA_CONTROL_DML_ROLE=kala_control_writer
   KALA_RUNTIME_DML_ROLE=kala_runtime_writer
   KALA_RUNTIME_READER_ROLE=kala_runtime_reader
   KALA_S3_ENDPOINT=https://objects.example.test
   KALA_S3_REGION=example-1
   KALA_S3_BUCKET=kala-runtime-eval
   KALA_S3_FORCE_PATH_STYLE=false
   KALA_PG_S3_EXTERNAL_BACKUP_ACK=1
   ```

   The acknowledgement is an operator assertion only; it neither configures backups nor proves restore viability. For source-only Compose, generate and securely retain a canonical random UUID in a private file outside the container, then set `KALA_INSTALLATION_ID_FILE` to its absolute path in the invoking environment. Do not regenerate this ID on retry or point it at an existing project. The one-shot `fresh-storage-claim` job must finish before either schema migration: it checks both databases and the **entire** bucket, then writes matching external installation markers into both PostgreSQL databases and S3. The claim job also binds the 32-byte Runtime state key fingerprint and one initial recovery checkpoint to both databases and S3. A matching three-marker set may be retried with the same UUID **only if all three recovery checkpoints also match**; after a failed Operator `install`, the Operator tears down the fresh Compose project including its disposable secret volumes before retry, never the external databases or bucket. If cleanup was interrupted and project containers, volumes, or networks remain, preflight refuses reuse; investigate those resources rather than deleting external markers or choosing a new UUID. Any partial/mismatched marker set requires manual recovery, not automatic marker deletion. It is not a distributed transaction or a substitute for coordinated restore.

For the **local-source bundle Operator** instead, use `init-config --storage postgres-s3 --identity external --acknowledge-evaluation --acknowledge-external-backup` with a new configuration directory and project. Current source selects PG/S3 and external OIDC if both options are omitted, but **never** waives either acknowledgement or provisions the external services. Fresh `setup` always stops with this manual-path instruction rather than installing a local Runtime volume; even explicit legacy `--storage local-volume|nfs|external-nfs --acknowledge-legacy-storage` cannot create a new Private Cloud installation. The PG/S3 `init-config` creates owner-only `storage-origin.json` and `installation-id`; retain both with the external backup/restore plan and never edit `KALA_STORAGE` to reuse a legacy config. Supply the external credentials, OIDC settings, provider catalog and 32-byte state key separately, then run `preflight` and `install`. `setup` cannot provision external credentials for this mode. Preflight validates the rendered claim/migration topology and rejects existing project containers, labeled volumes and networks but **does not itself inspect** the external databases/bucket; the claim job does so before migrations. No PG/S3 Operator upgrade, rollback, built-in backup/restore or uninstall is supported. Do not interpret a locally built bundle as a published signed release.

Before the first source-only apply, run:

```sh
node scripts/private-cloud-local/preflight.mjs
node scripts/private-cloud-local/validate-compose-policy.mjs
node scripts/private-cloud-local/deploy-profile.mjs apply
```

Source-only preflight checks secret-file shape/permissions, that both URLs select `runlab_control` and the writer role matches, distinct control migration and writer credentials, the disposable Runtime root, PostgreSQL login-state selection, absence of the Gateway control-data mount, disabled legacy database/init services, and the external database migration mode. It does not connect to PostgreSQL, inspect grants, configure TLS, or prove backup/restore; those remain operator preconditions. A failed claim may leave external markers behind. Preserve all three stores and their backups for forensic/manual recovery; do not delete a single marker and retry against mixed data.

## Failure and operational boundaries

- `fresh-storage-claim` uses the immutable installation ID, the 32-byte state key, the two migration-owner URLs and a **separate** bucket-scoped bootstrap S3 identity, with no local claim receipt volume. It rejects nonempty stores before migrations; the claim cannot atomically commit across PostgreSQL and S3. Both workload processes receive the same UUID as a read-only Compose config; on **every start**, Gateway reads the control and Runtime PostgreSQL markers using its steady-state writer/reader logins, and Runtime reads the Runtime PostgreSQL and S3 markers using its steady-state writer/S3 credentials. The migration jobs audit effective claim-marker write and owner privileges (including inherited privileges), then grant only `USAGE` on the claim schema and `SELECT` on its marker to PG workload roles. Source preflight and bundle Operator validate that the bootstrap and Runtime S3 access keys differ; **the object-store policy deny on the Runtime key must still be verified by the operator**, since configuration checks cannot attest provider IAM behavior. An absent, inaccessible, corrupt or different marker refuses service; never recreate/overwrite a marker to make a restore start. The source preflight and bundle Operator reject a rendered PG/S3 topology that omits the gate. Direct custom launchers that skip these profile controls have no such guarantee. For this source revision the workload processes also check a separate recovery checkpoint in their respective authorities: Gateway compares both PG checkpoints; Runtime compares Runtime PG, S3 and the 32-byte state master key fingerprint. A missing/partial/different set rejects startup. Equal checkpoints still **do not** prove equal snapshot timestamps when writers remained active or snapshots were taken at different times after a marker was written; external provider snapshot/version inventory, old credential revocation and real restore rehearsal remain required.
- `control-plane-init` receives only `control_postgres_migration_owner_url`, requires the target database to exist, and runs migrations before the Gateway starts. `runtime-ingress` receives only the projected `control_postgres_writer_url` and stores organizations, browser sessions, and OIDC login state in PostgreSQL. It does not mount `control-data`.
- `runtime-schema-init` receives only the Runtime owner credential and executes versioned migrations/scoped grants before `runtime-host` starts. Runtime and Gateway receive their separate writer/reader credentials. Schema migration and startup checks fail closed.
- `init-app-secrets` and `init-storage-secrets` copy restricted host files into owner-restricted named volumes so non-root services can read them. These volumes can be recreated from the source secret files and contain no authoritative application records, but their host-local lifecycle and the authority of the source secret files are not solved by this profile.
- `/var/lib/kala` is bounded disposable tmpfs. Confirmed Session/Queue/Artifact authority must survive replacement through Runtime PostgreSQL/S3. For new queued messages with uploaded attachments, the PG/S3 Runtime writes an operation-ID-keyed reference-protection event and the Queue item in one owner-fenced PostgreSQL transaction. A Queue failure rolls back both: the object remains a pending upload for bounded expiry/release rather than becoming an unconsumed committed reference. Single-Runtime release, pending expiry and confirmation are serialized; a PG event guard blocks stale cross-replica pending releases after protection (and rejects admissions after a concurrent release). Local source now commits a PG Session deletion tombstone before HTTP/Dashboard queue, Executor and object cleanup, prevents fresh Queue admission from crossing the tombstone with a PG projection lock, and runs bounded periodic owner-fenced cleanup retries. Gateway route tickets return distinct deleting/missing terminal states and a retryable relocating state; Dashboard prepares owners only for relocation. The single-Runtime evaluation profile does not exercise multi-node takeover; already-dispatched external effects, atomic tree deletion, legacy pre-protected orphan reclamation, real fault/recovery acceptance and a general admission ledger are still missing. Session fork now derives its child from the persisted creation state and durable event prefix and commits the child under PG ownership fencing before reporting success. File-based enhancement actions, including trace/profile/export, reject PG-backed Sessions even if a caller supplies a `rootDir`; these outputs are **not** available as durable PG/S3 artifacts. Other local-state paths still require capability audit and must not be assumed durable merely because they can write scratch.
- `KALA_RUNTIME_NODE_ORIGIN` and the Gateway allowlist/bootstrap origin identify the sole mTLS `runtime-host`. This is not placement failover or parallel execution; migration, drain, and cross-node takeover runbooks remain future work.
- The built-in local-volume backup and Unit export/restore explicitly refuse this profile. Operators must coordinate recoverable snapshots of both PostgreSQL databases, S3 objects/versions, secret source files, and the Runtime state key, then rehearse restore on **new application nodes/project with the original installation ID**, never by claiming a new installation UUID or rewriting the immutable claim. Restored stores must belong to one externally coordinated, write-quiesced recovery set; a matching UUID alone is not sufficient. Isolate the old nodes and revoke their old credentials before directing any write to the recovered stores. `deploy-profile.mjs apply` refuses an existing PG/S3 project because its automated backup cannot protect these authorities.
- Do not infer Enterprise Pilot acceptance, customer-network compatibility, supported-version upgrade/rollback, all-local-authority removal, or multi-Runtime continuity from this evaluation profile.

## Offline recovery-set boundary (source-only, not built-in backup/restore)

For a fresh PG/S3 evaluation install, the claim job creates a separate checkpoint (`checkpointId = installationId`) in both PostgreSQL databases and `_kala/recovery-checkpoint.json` in S3, bound to the SHA-256 fingerprint of the Runtime state master key. The workload roles need SELECT/GET only; the bootstrap S3 policy must allow conditional `PutObject` for this second reserved key, including `If-Match` for later checkpoint changes. An older installation with only UUID markers and no recovery checkpoint **fails closed** at migration/startup; do not fill in a missing checkpoint automatically on nonempty stores.

An operator may prepare an **offline** backup boundary using the source-only `packages/host/dist/bin/kala-recovery-checkpoint.js`. First stop Gateway and **every** Runtime, block their old credentials from both PostgreSQL databases and S3, and confirm no other writer/retention job is active. Back up the installation ID, key and all secret sources independently. Generate and durably record a fresh canonical UUID for `KALA_RECOVERY_NEXT_CHECKPOINT_ID`; pass the existing checkpoint as `KALA_RECOVERY_PREVIOUS_CHECKPOINT_ID`. Run the CLI with `--acknowledge-all-writers-stopped`, supplying `KALA_INSTALLATION_ID_FILE`, `KALA_RECOVERY_STATE_MASTER_KEY_FILE`, `KALA_RECOVERY_CONTROL_DATABASE_URL_FILE`, `KALA_RECOVERY_RUNTIME_DATABASE_URL_FILE`, `KALA_RECOVERY_S3_ACCESS_KEY_ID_FILE`, `KALA_RECOVERY_S3_SECRET_ACCESS_KEY_FILE`, `KALA_RECOVERY_S3_ENDPOINT`, `KALA_RECOVERY_S3_REGION`, `KALA_RECOVERY_S3_BUCKET` and `KALA_RECOVERY_S3_FORCE_PATH_STYLE` via restricted files/environment as appropriate. Use only operator owner PG roles and the one-shot bootstrap S3 identity; this CLI is deliberately **not** a bundle Operator backup/restore command. If any write fails, keep all workloads stopped. Retry only with **the identical** old/new IDs and `--resume-partial` after investigation; do not issue a new checkpoint or silently rewrite an installation marker. Once all three checkpoints agree, keep writers stopped while taking provider-native snapshots/PITR boundaries of both PG databases and an inventory of the matching S3 object **versions**, plus key/secret source backups; record those version IDs and the checkpoint ID in an external operator-controlled backup manifest. Only then may normal traffic resume with appropriately reissued workload credentials. Rehearse restoration on new nodes with the original installation ID, restored key and all matching versions, old nodes isolated and old credentials revoked. Failure to prove any condition means **do not restore service**.

This protocol rejects *different checkpoint IDs* on startup and a wrong key, but **does not prove** that two snapshots stamped with the *same* checkpoint were taken at a consistent time, that writers were actually stopped, that external backup data survived, or that old owners cannot reach restored endpoints. It does not implement the provider snapshot/restore operation or HA failover. The PG/S3 Operator still refuses built-in backup/restore; real PG/S3 recovery and stale-owner fault acceptance remain outstanding.

## Operator-gated, source-only two-Runtime experiment (not an Operator upgrade)

The optional `compose.storage-postgres-s3.parallel.yaml` overlay is **not** part of the signed-bundle Operator installation, the default profile, or a production HA claim. Do not apply it to an existing `local-volume`/NFS installation. It requires the same external PG/S3 authorities as the single-Runtime evaluation and current versioned Runtime schema. Per the [Runtime placement protocol](../architecture/private-cloud-runtime-units.md), enabling `parallel-v1` for one logical Unit is **irreversible under the current schema**; stopping the second container does not restore exclusive placement.

1. Prepare a separately backed-up source-only PG/S3 evaluation installation, provision the Organization and record its authoritative `(organizationId, unitId)` from the control PostgreSQL mapping. Preserve the external installation ID, both PostgreSQL databases, the S3 bucket/versions and the state key. Stop the Gateway and **all** Runtimes and isolate any old Runtime processes before changing placement; no client traffic or control-plane reassignment is allowed during the operation. Wait for the exclusive placement lease, every membership, and every Session/Task owner to expire. A nonempty `tenant-data` volume or a local-only Session is not eligible for this operation.
2. Inspect the Runtime PostgreSQL `tenant_runtime_unit_placement_leases` row and record its generation. Choose `--expected-generation` exactly one greater. A Unit without an existing exclusive placement row is **not** eligible: materialize it exclusively, stop it, and then inspect its expired lease. Never invent generation 1 from an absent row, which could indicate a partial restore. The schema-operator-only command `packages/host/dist/bin/kala-parallel-placement.js --organization-id ORG --unit-id UNIT --expected-generation N --acknowledge-irreversible` requires `KALA_PARALLEL_CONTROL_DATABASE_URL_FILE` (control database operator read access) and `KALA_PARALLEL_RUNTIME_DATABASE_URL_FILE` (Runtime schema owner). Pass file paths, never credentials on the command line. It checks the control Organization→Unit binding, current migrations, exclusive lease, live memberships/owners and acknowledged generation, then installs the permanent barrier and feature gate in one Runtime PG transaction. It refuses a missing row or an active owner and cannot make external database snapshots atomic. A successful retry with the same generation is idempotent; an inconsistent partial state or failed post-commit binding recheck requires manual investigation, **not** deletion of a gate or an installation marker.
3. Generate and securely retain a canonical base64url-encoded 32-byte random `runtime_routing_ticket_key` under the existing restricted secrets directory. Apply `compose.postgres-s3-base.yaml`, `compose.storage-postgres-s3.yaml`, and **then** `compose.storage-postgres-s3.parallel.yaml` as one source-only Compose project; keep the existing installation UUID and external stores. The overlay supplies a second disposable Runtime with a unique DNS origin/node ID, the same externally backed PG/S3 and state key, a two-origin Gateway allowlist, a restricted Gateway-only ticket key, and owner-derived Session tickets. Both Runtime origins use the same internal mTLS server identity (`runtime-host`) for this limited Compose experiment; a production deployment needs separately managed per-replica identities and customer-network acceptance. Do not start the overlay before the per-Unit gate and credentials are verified. Provision/reconcile the **same** Unit lifecycle generation on both replicas; two container healthchecks alone do not prove either has a ready Unit.
4. Accept the experiment only after verifying two live memberships, independent X/Y Session owners, routed browser reconnect following a lost Runtime, stale-generation rejection, pending Session deletion recovery, Executor receipts, and fault-tested S3/PG behavior. Gateway remains a single process here; loss of its host, both databases, S3, credentials, or a disputed backup snapshot is not solved by the second Runtime. Stop traffic and investigate any `session_relocating` loop rather than falling back to a shared Unit socket. Neither source-only overlay nor local tests certify a supported release, HA, coordinated restore, or an in-place upgrade.

## Scheduled-principal authorization service (local source)

The Runtime service injects a control-authority client into each Unit. Set `KALA_RUNTIME_AUTHORITY_ORIGIN` to a reachable Gateway service origin; the PG/S3 base and parallel-B source Compose profiles default to `http://runtime-ingress:13001`, and the Dedicated AppHost source uses `http://gateway:13001`. These HTTP defaults are for the existing isolated single-host/evaluation network, **not** authenticated cross-failure-domain transport or a production-HA recommendation. A remote operator must provide a protected HTTPS service/LB origin and normal trusted CA configuration (Node's `NODE_EXTRA_CA_CERTS` may supply a private CA); do not disable certificate validation. Full production workload identity/mTLS and secret rotation remain separate acceptance gates. Redirects are rejected so a service credential is not forwarded to a different origin.

`POST /internal/background-authority` is a service-authenticated decision endpoint, not a browser API or proxy route. It uses the existing protected ingress service credential, rejects cookie/Authorization/Origin browser requests, limits input to 4 KiB and bounds the decision to five seconds. The Gateway derives current human membership/role or service-account scope/revocation/expiry and exact Organization/Unit/active contract from control PostgreSQL. Runtime receives only a current role decision and needs no control-database credential. The selected origin can front multiple Gateways sharing that authority; this configuration alone does not prove HA, load or independent fault domains.

The Gateway may start after Runtime readiness. Missing/unavailable authority must retain claims rather than falsely mark them failed, and pending queue work is checked again before model/Shell dispatch. An unavailable pre-dispatch check releases its non-executed claim and enters a bounded local retry pass; explicit denial leaves the accepted operation blocked for inspection/Stop rather than changing identity. Already-started effects keep the existing unknown/receipt policy, not this pre-dispatch retry policy. Browser logout alone is not schedule revocation; current principal/Organization authority is what matters.

Delegated queue content is immutable. Only its original principal can edit/resume a schedule; Owner/Admin can pause/delete another principal's definition but cannot rewrite or resume it under that identity. Create a new definition to delegate your own authority. Old scheduled queue entries without durable attribution fail closed and need explicit inspection/Stop/recreation, never guessed attribution. Versioned persisted modes and metadata envelope v4 make older readers reject newly delegated work instead of ignoring its authorization field. Drain/upgrade all old scheduling replicas before enabling the policy; do not roll back while delegated work is pending. This is Organization/principal enforcement, **not** the still-unimplemented end-to-end Workspace grant and broadcast/list isolation capability.


## External secret references (source-only, opt-in)

The [deployment-mode contract](../architecture/deployment-mode-contract.md) is the secret-lifecycle SoT. Runtime and Gateway now share a **Node-only** `@agent-kernel/shared/secret-resolver` entry point. This is not a new secret store and does not provision OpenBao, an issuer, workload policies or HA. The stock Compose evaluation profiles still copy local bootstrap files; they do not automatically forward the following variables from a host environment file. Inject them into the actual workload through operator-owned manifests/overrides. Existing installations are unchanged.

Select `KALA_SECRET_RESOLVER=openbao-jwt` with these operator-controlled values:

| Variable | Meaning |
|---|---|
| `KALA_OPENBAO_ADDR` | Explicit HTTPS origin, with no credentials, path, query or fragment |
| `KALA_OPENBAO_AUTH_MOUNT` | Single-segment JWT auth mount, for example `workload` |
| `KALA_OPENBAO_ROLE` | Workload-specific JWT role, not a user-selected role |
| `KALA_OPENBAO_JWT_FILE` | Read-only projected JWT supplied and rotated by the workload issuer/platform |
| `KALA_OPENBAO_KV_MOUNT` | Fixed single-segment KV-v2 mount, for example `kala` |

Use normal TLS verification; a private CA may be supplied by Node's `NODE_EXTRA_CA_CERTS` at process startup. Never disable certificate validation. `KALA_OPENBAO_ALLOW_LOOPBACK_HTTP=1` permits only explicit loopback HTTP for isolated evaluation and must not be used as a production transport setting. No static OpenBao root token or long-lived service token is accepted by this adapter. Use an operator-managed active/forwarding service endpoint: the client deliberately refuses leader/HTTP redirects, so an HA front door must not depend on the client following them.

Configure the OpenBao JWT role with verified issuer/signing keys, bound audience and workload claims (including the intended service identity), a read-only policy restricted to that workload's required paths, and issued token TTL/max TTL of **at most 60 seconds**. The adapter rejects longer issued leases, caches only the short login token in memory, and never renews it or persists it. Each resolution rereads the projected JWT; a changed JWT forces a new login and an unreadable JWT denies resolution. Cached-token reuse ends before its lease/60-second bound. Revoke outstanding OpenBao tokens when immediate identity revocation is required; changing the issuer's grant alone does not invalidate already-issued tokens. Use separate Gateway/Runtime identities and policies. Auth mounts and KV mounts are fixed by the operator, not chosen by the reference.

Provider catalogs retain their existing structure/model refs; change only the relevant `credentialRef` to `bao:providers/openai#apiKey`, for example. It reads field `apiKey` from the fixed mount's KV-v2 `providers/openai` path. Empty/malformed refs, traversal and missing/non-string fields fail closed. Selecting OpenBao does not enable mixed `file:`/`env:` refs or fallback to a local provider secret. Each new top-level LLM call reads the current value; an in-progress call/stream keeps its admitted credential and is not replayed for rotation. A denied read does not silently reauthenticate and dispatch; a later independent call may log in again if currently authorized.

A minimal **operator-owned Provider-only** override for the existing Runtime service looks like this (supply a catalog containing `bao:` refs through the existing `KALA_PROVIDER_CATALOG_FILE` selection):

```yaml
services:
  runtime-host:
    environment:
      KALA_SECRET_RESOLVER: openbao-jwt
      KALA_OPENBAO_ADDR: https://secrets.example
      KALA_OPENBAO_AUTH_MOUNT: workload
      KALA_OPENBAO_KV_MOUNT: kala
      KALA_OPENBAO_ROLE: kala-runtime
      KALA_OPENBAO_JWT_FILE: /run/kala-identity/jwt
    volumes:
      - ${KALA_RUNTIME_IDENTITY_DIR:?operator-projected identity directory}:/run/kala-identity:ro
```

Mount the **directory**, not one immutable JWT inode, so atomic projection replacement is visible. A parallel `runtime-host-b` needs its own configured identity directory/role and the same resolver selection; do not assume the first service's override is inherited. This snippet is not a complete deployment, does not remove the evaluation init service's local-file prerequisites and has not been applied to an existing environment.

For names already read through `readRequiredSecretEnv`, choose exactly one nonempty `NAME`, `NAME_FILE` or `NAME_REF`. `_REF` uses the selected resolver; missing selection or external failure never falls back to local values. In particular, Runtime's environment-based `KALA_RUNTIME_HOST_LLM_API_KEY_REF` also resolves per call. Runtime PG/S3 credentials, Gateway control-PG/Runtime-reader connection strings, OIDC client secret, ingress/session secret and routing-ticket key can be resolved at startup through their existing names plus `_REF`; clear the corresponding nonempty direct/`_FILE` setting in an override. A configured control-PG ref must not fall back to JSON control stores when resolution fails.

These bootstrap consumers still capture values for their lifetime. Rotate them with coordinated drain/replacement, compatible peer credentials and health-check configuration; this work does not rotate existing DB pools/S3/OIDC clients or ingress/routing keys in place. TLS certificate paths and the Runtime state master-key file remain separate file/recovery boundaries, not generic `_REF` consumers. Preserve the correct state encryption key with the durable recovery set; replacing it is not credential rotation. Native SDK/third-party credentials outside this factory also retain their own lifecycle. Do not label the full installation file-free or secret-recoverable from this adapter alone.

Resolution is bounded to five seconds, JWT input to 64 KiB, and each service response to 256 KiB; redirects are rejected. Denial, authority unavailability and configuration errors contain no external response body, JWT or secret value. No positive secret-value cache or automatic model retry is added. Source verification uses the fixed OpenBao 2.7.2 image in a random-name disposable dev container with synthetic identity/secret data and a local HTTP Provider fixture; it is not real OIDC/model/SDK, verified production TLS, OpenBao failover/unseal, backup/restore or performance acceptance. Run the opt-in case with `KALA_RUN_OPENBAO_INTEGRATION=1` and Host's `src/llm/openbao.integration.test.ts`; the container and tiny identity scratch are cleaned in `finally`.


## Durable webhook worker (source-only, opt-in)

Authority is the deployment-mode contract's external-delivery boundary; this is an operational source profile, not a new SoT, default installation or production-HA declaration. Use `compose.webhook-worker.yaml` **after** `compose.postgres-s3-base.yaml` and `compose.storage-postgres-s3.yaml`, with a newly built immutable Gateway image containing migration 0008 and `kala-webhook-worker`. The existing Dedicated images/DB have not been changed by this source work. Reuse the image, not Gateway credentials. Do not start a worker from older images against schema 8; schema matching is exact.

Activation order:

1. Stop **all** old webhook workers and drain their HTTP work before schema expansion. Mixed old/new worker protocols and rollback to the old worker are unsupported. Take the normal coordinated backup and retain its compatible image pins; do not run the fresh-install claim tool on populated stores during upgrade.
2. The operator pre-creates a separate standalone PostgreSQL LOGIN role with no memberships/ownership, schema/database CREATE, superuser, role/database creation, replication or bypass-RLS power. Set `KALA_WEBHOOK_WORKER_ROLE` for the owner-only control-plane initializer, distinct from `KALA_CONTROL_DML_ROLE`. The initializer migrates and grants SELECT on event/endpoint/delivery/schema and claim tables, INSERT on deliveries, and UPDATE only on fan-out/delivery progress columns. Effective-privilege auditing fails closed on inherited/public excess table/column authority and executable user-schema SECURITY DEFINER escape paths; harden unexpected PUBLIC grants rather than giving the worker an app/owner credential. Gateway producers retain SELECT and six envelope INSERT columns only; they cannot insert fan-out state or rewrite events/deliveries. Audit/Usage lifecycle permissions are explicitly **not yet closed**.
3. Migration 0008 marks pre-existing unresolved events `legacy_review`; previously delivered/dead legacy events are `complete`, never automatically fanned out. Only new events default to `pending`. Review unknown remote effects and receiver deduplication before any deliberate legacy replay. No bulk replay/admin tool is delivered here. Do not blindly change all legacy rows to pending.
4. Provide only the worker login URL as `database_url` in `KALA_WEBHOOK_SECRETS_DIR`, and a separate projected workload JWT as `token` in `KALA_WEBHOOK_IDENTITY_DIR`. Mount dedicated directories read-only, traversable/readable by uid/gid 65532; never mount the shared Gateway/Runtime/S3 secret directory. Directory mounts preserve projected-token replacement. Supply the installation UUID config and the Private Cloud deployment config. Startup checks exact schema, effective privileges, and control-PG installation/recovery marker consistency; it needs no Runtime-PG/S3 credential. DB bootstrap accepts exactly one `KALA_WEBHOOK_DATABASE_URL`, `_FILE` or `_REF`; pools remain pinned until replacement.
5. Set comma-separated **exact HTTPS origins** in `KALA_WEBHOOK_ALLOWED_ORIGINS` and the overlay's dedicated OpenBao address/auth-mount/role/KV-mount variables. Endpoint URLs cannot contain credentials, query or fragment; redirects are refused. Endpoint `secret_ref` is an object containing `ref: "bao:organizations/<organizationId>/webhooks/<key>#<field>"`. The root rejects another Organization's prefix; OpenBao policy must independently restrict the workload's reads. Reference values resolve on every attempt, permitting rotation behind the same reference. Operator-controlled DNS, egress policy and TLS trust remain required; source allowlisting is not provider/network-isolation certification. Loopback HTTP requires explicit isolated-evaluation flags for both the webhook and resolver and is not enabled by this overlay.
6. Explicitly add the overlay and scale `webhook-worker` as needed. It has no published port, container name or application-data volume; all progress is in PG. Size PG connections/recipient traffic for four connections and four concurrent attempts per replica. Defaults: 20 events per fan-out transaction, at most 100 recipients per event, 50 claims per batch, 10-second whole-attempt deadline below a 30-second DB-clock lease, ten attempts with 5-second exponential backoff capped at one hour, 64-KiB source payload/body bound, and 30-second idle polling (due times are eligibility, not exact dispatch deadlines). Excess recipient count or a malformed legacy reference blocks that event with a normalized reason rather than crashing the entire queue. `KALA_WEBHOOK_ONCE=1` runs **one batch**, not an unbounded drain.

Recipients are enabled topic/tenant matches visible at first fan-out whose registration timestamp is no later than the event. Later registrations receive no history. Fan-out snapshots URL, reference and endpoint generation; disabling/logically deleting or retargeting invalidates old snapshots even if subsequently reversed. Invalid snapshots cancel at the next attempt. Physical deletion is restricted by retained delivery history; use disable for logical deletion. Already-dispatched remote effects cannot be revoked by a DB fence. Successful endpoint deliveries do not replay when another endpoint fails. Legacy event-level `delivered_at`/retry fields are historical, **not** the new completion view: inspect `webhook_fanout_state` and per-endpoint `webhook_deliveries.state`.

Delivery is **at least once**. The stable `x-agent-runlab-delivery-id` is SHA-256 of the JSON event/endpoint pair, independent of lease generation, process and retries; `x-agent-runlab-event-id` and per-attempt HMAC remain present. Receivers must verify `x-agent-runlab-signature` over the exact request body and deduplicate by delivery ID. A crash/timeout may happen after remote acceptance, so lease expiry can repeat the same ID. This explicit webhook retry contract does not permit replaying an Agent/tool's unknown external effect. Error persistence is restricted to fixed codes and HTTP status, never raw exception/response body/secrets. SIGTERM stops claims, aborts active attempts/sleep and closes PG/telemetry; unfinished claims can expire safely. Quiet background DB operations use aggregate telemetry rather than independent business traces; no per-tenant/event/endpoint metric dimensions are added.

Local acceptance: enable `KALA_TEST_WEBHOOK_DELIVERY=1` (and `KALA_TEST_DOCKER_SUDO=1` where required) for `packages/runtime-ingress-gateway/src/webhooks/outbox-worker.test.ts`. It creates/removes only its own bounded temporary PG using cached `postgres:16-alpine`, plus local recipient and controlled secret-protocol fixtures. The normal suite intentionally skips this integration gate unless enabled. It is not a real customer secret service, TLS/issuer, immutable-image deployment, process-SIGKILL recovery, cold restore, sustained load/fault-domain HA or signed release gate. Subscriber management, replay/archive policy and durable delivery monitoring remain separate work.
