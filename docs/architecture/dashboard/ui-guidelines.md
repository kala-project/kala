# Dashboard UI 规范

本规范适用于 Kala Dashboard、Settings、工作区接入和管理界面。
“必须”和“禁止”是实现与审查要求，不是视觉建议。

## 1. 先回答用户的问题

- 页面必须说明：这是什么、当前状态是什么、用户可以做什么。
- 功能只读或由他人管理时，必须给出具体配置位置、可执行的入口或应联系的角色。
- 禁止删除配置表单后，只留下“由管理员管理”而不说明去哪里配置。
- 禁止使用未解释的产品名代替功能名。例如，必须区分“后端服务”、
  “Kala Agent 引擎”“GitHub Copilot Agent 引擎”“模型供应商”和“模型”。
- 业务名称优先。组织 ID、进程 PID、内部路径、协议版本等放入技术详情，
  不得成为主标题或占据主要视觉空间。

## 2. 普通设置与管理设置分开

- 普通用户的个人偏好、通知和可用模型，与组织管理设置分组呈现。
- 普通用户必须能查看自己有权访问的工作区。工作区浏览与接入邀请、令牌、
  吊销等管理操作必须分开，普通浏览不得请求管理员专属 API。
- 模型配置统一放在“模型”中。管理员直接编辑共享供应商、Base URL、
  写入式密钥和模型信息，普通用户查看可用模型；不得用部署文件说明替代已有配置能力。
- 组织管理员与部署管理员不是同一个权限概念。Private Cloud 的组织 Owner
  不自动拥有全局部署诊断权限。
- Dedicated 的部署管理入口必须以服务端确认的 Owner 权限为依据。
- 无权限的管理标签不展示；有权限但尚未配置的功能，必须说明配置入口。
- 前端隐藏不是权限控制。管理 API、Socket.IO namespace 和代理入口必须独立鉴权。
- 桌面侧栏、窄屏选择器和深链接必须使用同一份可见标签集合。

## 3. 渐进披露，不堆砌说明

- 字段标签、当前值、状态、必要操作必须直接可见。
- 原理、范围、实现细节、长篇描述放入一致的信息提示或可展开详情。
- 禁止在表单、卡片、每条列表记录下重复相同的说明性小字。
- 禁止在账号菜单加入产品口号、路由宣传语或与账号操作无关的文案。
- 账号必须显示真实登录名或账户资料，Owner 等权限名称只能表示角色，
  不得替代账户名。显示资料与不可变的授权主体必须分开保存。
- 错误、保存结果、即将丢失的一次性凭据等当前操作必须知道的信息直接显示，
  但应简短、相关，并给出下一步操作；不得藏在帮助提示里。
- 信息提示必须支持键盘、触摸和屏幕阅读器，不能依赖鼠标悬停。

## 4. 布局必须经得起真实数据

- 设置内容使用受约束的容器；网格与 Flex 子项必须允许收缩。
- 断点应考虑设置侧栏占用后的实际内容宽度，不能仅按整个窗口宽度增加列数。
- 长 ID、URL、命令、令牌、翻译文案不得撑开布局、挤压表单或覆盖操作按钮。
- 列表操作使用明确的布局区域。禁止让一整段说明文字撑大不收缩的操作列。
- 窄屏按顺序堆叠字段与操作；不得通过隐藏溢出来掩盖内容或按钮不可达的问题。
- 可以截断可复制的技术标识，但不得截断错误原因、主要名称或关键业务数值。
- 主要正文和字段使用正常可读字号。禁止靠缩小文字塞入更多内容。

## 5. 统计数字必须有单位、范围和时间

- 存储容量使用可读单位，例如 `19.2 MiB / 10 GiB`，而不是无解释的大整数。
- 文件数、已存储大小、上传预留、配额分别展示，不能把预留误称为已存储文件。
- 必须说明统计覆盖什么、不覆盖什么。例如，附件和产物的对象占用不等于
  PostgreSQL 磁盘大小、整个 S3 桶大小或 Executor 工作区磁盘大小。
- 未获得的统计显示“未提供”或明确错误，禁止用 `0` 假装有测量结果。
- 状态快照显示更新时间。实现名称和原始字节数可以放入技术详情。

## 6. 刷新以实际需求为准

- 默认进入页面时读取一次，并提供明确的手动刷新。
- 昂贵的存储统计不得扫描工作区目录、下载对象或枚举整个桶来刷新设置页。
  优先读取带组织约束的持久化计量索引。
- 不得为只读设置、关闭的弹层或隐藏的面板增加短周期 HTTP 轮询。
- 实时业务变化优先复用 Socket.IO。只在实际相关变化或重新连接时刷新，
  不得把定时轮询改成“每条普通消息都重新 GET”。
- 如确需自动统计刷新，周期必须与成本相称，长周期、可见时才执行，
  且不能因重渲染、焦点切换或多个标签页放大读取。
- 操作进度可有有界的临时跟踪，完成、失败或关闭后必须停止。

## 7. 管理入口必须真实、明确且安全

- 有权限的管理员必须能从清楚标记的管理区域找到可观测性和连接诊断。
- Aspire 使用原生界面，不在 Kala 中抽取或重新展示遥测数据。提供实际部署地址、
  端口和必要的访问限制说明；只显示少量工具入口时，复用现有管理区域，不新增空洞页面。
- “打开 Socket.IO Admin”必须是可访问的控制台，而不是没有去向的禁止访问说明。
- 不得为了让链接可用而关闭认证、暴露 OTLP/API 密钥、泄漏令牌到 URL，
  或开放未经保护的端口。
- 使用当前受信任的部署入口和本机已有、锁定的官方资源。新增部署入口或权限边界
  必须明确说明，不能偷偷改变。

## 8. 交付前检查

- 使用真实权限数据验证普通用户、组织管理员和 Dedicated Owner 的可见内容。
- 验证 320/390 像素窄屏、常规桌面，以及设置侧栏存在时的中间宽度。
- 验证长工作区名、长 ID、多个邀请、已撤销/过期邀请和空数据状态。
- 检查字段与按钮不重叠、无需横向滚动、键盘可达、帮助提示可关闭。
- 检查模型配置位置清楚、存储统计单位正确、管理链接能实际打开。
- 检查空闲网络请求；不能只检查界面截图或以降低观测采样掩盖多余请求。
- 架构、鉴权或持久化迁移必须逐项核对原有能力的 UI、API、保存位置和实际执行；
  不得把“使用平台架构”解释为“删除高级设置”。接入模式与权限选项必须传到安装器、
  服务配置和操作系统，不能只改变按钮或命令标题。
- Operator 管理不等于功能禁用。Hooks 等执行能力必须接入实际运行链路；
  无法加载指定的策略配置时必须报错，不得悄悄变成空策略。
