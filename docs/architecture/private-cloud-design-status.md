# Private Cloud design, delivered scope, and outstanding gates

**Status:** implementation/evidence index as of 2026-10-21, not a new architecture contract or a production-support declaration.

**Single source of truth by question:** the [enterprise architecture contract](./private-cloud-enterprise-architecture-contract.md) defines the *target invariants* (including per-resource fencing for concurrent replicas); the [deployment-mode contract](./deployment-mode-contract.md) defines product naming and composition rules; the [Pilot matrix](./private-cloud-enterprise-benchmark-matrix.md) defines the release gate. For *what actually starts by default*, use the signed-bundle [Operator storage selection](../../scripts/deploy/kala-private-cloud.mjs) and the exact version's [first-install guide](../operations/private-cloud-first-install.md), not a source-only Compose profile. The [Runtime implementation record](./private-cloud-runtime-units.md) describes delivered single-node code and operator-gated experiments; this ledger compares that evidence with the target. The [release record](../operations/private-cloud-release.md) binds results to an exact asset; the [support policy](../operations/release-support-policy.md) alone defines support claims. If a first-release assumption conflicts with the enterprise target, label it a gap rather than silently replacing the target. Code presence, a checked implementation phase or an experimental run never constitutes Pilot acceptance or release certification.

## Product and trust path

Private Cloud is a self-hosted, Organization-scoped Agent platform, not one Host per browser user. An operator provisions the Organization and its contract; the first visitor cannot create an Organization just by signing in. Organization membership and Workspace grants authorize users; one Organization maps to one **logical** TenantRuntimeUnit in the initial topology. Members enter one Kala product Origin. The Gateway validates OIDC identity `(issuer, sub)` and a revocable browser session, checks control-plane permissions and placement, strips caller-supplied routing credentials, and sends a trusted route to a private Runtime. Unit-owned Agent state must not leak across Organizations. Customer-managed Executors enroll with a one-time invitation and initiate their own outbound TLS/WSS connection to the Gateway; human browser sessions are not machine credentials. Dedicated and Private Cloud share Agent semantics but have different composition/capabilities; Benchmark/Evaluation are disabled in Private Cloud.

PostgreSQL is the control-plane authority for Organizations, membership, policy, session revocation, audit and usage. The enterprise target also calls for secret references resolved by OpenBao, S3-compatible object bytes, observability, lifecycle governance and eventually storage-independent, fenced Runtime placement. These target components are **not all part of the current default install**. The optional bundled ZITADEL identity mode includes an `identity-proxy` (Caddy) for identity requests only; the Kala application entrypoint is `runtime-ingress`. External OIDC does not require that bundled identity proxy. The signed default quick-install binds both entrypoints to loopback; remotely accessible HTTPS and its identity issuer require separate operator configuration and verification.

These outstanding Pilot gates are **separate** from production multi-Runtime failover.

## Deployment and release boundaries

1. **Legacy installer, not the recommended Private Cloud target:** the currently published signed installation still starts one Docker host and one Runtime Host with multiple logical Units, defaulting to `local-volume`, with optional bundled identity or external OIDC. Its Runtime and bundled control PostgreSQL rely on local named volumes; the quick path is loopback HTTP. This is *noncompliant* with the node-independent Private Cloud persistence invariant and must not be advertised as a scalable/HA installation. Do not erase or silently migrate existing user data. The new PG/S3 evaluation profile externalizes control and Runtime PostgreSQL and S3 (external OIDC is required for the bundle route), but not host secret authority, and it has not completed all Runtime capability/recovery gates; it is not a substitute for an accepted customer deployment.
2. **Enterprise Pilot:** the [Pilot minimum](./private-cloud-enterprise-benchmark-matrix.md#pilot-release-minimum) is a *separate* acceptance checklist covering enterprise identity/authorization, customer Executor, governance, observability, support and signed releases. Passing Runtime implementation phases or a local fresh-install replay does not check off all of it.
3. **Multi-node target:** shared PG/S3 state, owner leases and generation fencing, storage-independent placement, safe external effects and client continuity. `parallel-v1` proves only the explicitly documented experimental scenarios in the [Runtime record](./private-cloud-runtime-units.md); no production multi-node support is claimed.
4. **Publication versus certification:** a signed, publicly downloadable GitHub Release is not automatically the stable *supported* release. The [release record](../operations/private-cloud-release.md) distinguishes the local beta.19 replay from a successful GitHub-hosted fresh-candidate run and from a real supported-predecessor upgrade. The current code/worktree must not inherit evidence from an earlier asset.

**Installer transition rule:** a new externally persisted installation may first be offered as an explicit, fresh-project **evaluation** route in the bundle Operator, with external OIDC, separate externally operated control/Runtime PostgreSQL databases and S3, restricted workload credentials, no inherited local application-data mounts, and explicit refusal of unsupported backup/restore or in-place upgrade. Including this route in a signed bundle does **not** make it the default or production-supported. Existing `local-volume`/NFS configurations and their volumes must remain readable and untouched until a separately rehearsed data migration, coordinated restore, capability audit and exact-asset acceptance justify a new default. Do not disguise source-only Compose as an Operator path or flip an installation's storage switch without moving its data.

Before changing any status here, link the exact implementation, default deployment configuration, acceptance result and supported release decision. Unknown or untested is **not** “passed,” but it is also not proof a feature is absent from the source tree.
