# Kala Product API v1

Kala exposes the Runtime's existing durable Session and DAG authorities through
`/api/v1`. The API does not maintain a second Session store or a separate task
graph.

The OpenAPI 3.1 document is available at `GET /api/v1/openapi.json`. Successful
and error responses include `X-Kala-Api-Version: v1` and
`X-Kala-Api-Compatibility: 1`; errors use:

```json
{
  "error": {
    "code": "invalid_request",
    "message": "operationId is required",
    "requestId": "opaque-request-id"
  }
}
```

## Authentication and tenant scope

Private Cloud accepts either the existing authenticated browser Session or a
Service Account bearer token. Service Accounts are created by an organization
owner or administrator through `POST /api/v1/service-accounts`; the plaintext
token is returned once and only its hash is stored.

`workspace:read` permits read endpoints and `workspace:write` permits mutation
endpoints. The Gateway resolves the token to exactly one organization and
Runtime Unit, removes caller-supplied authority headers, and injects the trusted
Unit, organization, and principal context. An invalid bearer token never falls
back to a browser cookie.

Dedicated deployments use their configured Host bearer authentication. Raw
Private Cloud authority headers are rejected outside a multi-tenant Runtime
Unit.

## Resources

| Method | Path | Behavior |
|---|---|---|
| `GET` | `/api/v1/sessions` | Cursor-paginated Session summaries |
| `POST` | `/api/v1/sessions` | Idempotent Session creation |
| `GET` | `/api/v1/sessions/{sessionId}` | Session summary and current state |
| `DELETE` | `/api/v1/sessions/{sessionId}` | Delete the Session and descendants |
| `POST` | `/api/v1/sessions/{sessionId}/messages` | Durably admit a user message |
| `GET` | `/api/v1/sessions/{sessionId}/dag` | Read the authoritative DAG run |
| `POST` | `/api/v1/sessions/{sessionId}/dag/decisions/{decisionId}` | Answer a pending decision |

Create requests require a stable `sessionId` and `operationId`. Retrying the
same create returns the existing Session; changing immutable creation fields
returns `409 conflict`. Message and DAG decision retries use their durable
`operationId`. Delete requires `Idempotency-Key` and returns `204` when the
Session is already absent.

List cursors are opaque. Clients must not parse them and should pass
`nextCursor` back unchanged.

## Typed client

`@agent-kernel/shared` exports `KalaApiClient` and the request, response, page,
Session, DAG, and error types:

```ts
import { KalaApiClient } from '@agent-kernel/shared'

const kala = new KalaApiClient({
  baseUrl: 'https://kala.example',
  token: process.env.KALA_SERVICE_ACCOUNT_TOKEN,
})

const session = await kala.createSession({
  operationId: 'create-release-review',
  sessionId: 'release-review',
  executionMode: 'dag',
})
```
