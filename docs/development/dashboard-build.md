# Dashboard resource-bounded builds

The shared development machine is not a disposable builder. Do not solve browser build OOM by raising the former 4 GiB build-script heap, stopping unrelated services, clearing developer caches or allowing unbounded parallel packaging. Build/typecheck must run sequentially; start with a 1536 MiB Vite old-space budget, one esbuild CPU and a bounded Rollup file-operation budget. Serialize sibling worker bundles (including Monaco language workers), but allow nested worker builds to avoid parent/child deadlock; release the gate on errors. Keep all existing language features, production minification, PWA and self-hosted hashed worker assets.

Verification builds on this Linux workstation must additionally run in a build-owned systemd resource unit with a **2304 MiB total memory cap, zero swap allowance, one CPU and bounded runtime/tasks**; heap limits alone do not cap RSS/native child processes. Inspect actual process/unit peaks and exit status. Failure is a failed build, not permission to increase budgets or a successful acceptance. These limits apply only to the new build unit, never to in-use Runtime/Executor services.

The first serialized-Worker experiment hit its 240-second runtime limit; native Monaco deduplication then passed all five real-worker boot tests but the complete app still exhausted the 1536 MiB Node heap (58.965 seconds, 1.9 GiB unit peak, zero swap). Neither is successful acceptance. The next reduction keeps Shiki and Mermaid as the same lazy ESM namespaces, including every language/theme/diagram, but packages their independent lazy graphs with Vite's locked native compiler. Emit only local content-hashed scripts/chunks; rewrite the existing runtime dynamic imports to Rollup-managed asset URLs after TypeScript stripping, retain source maps for profiling, and keep PWA navigation-shell-only precaching. No CDN, deleted feature, raised budget or changed highlighter/render API is allowed. Verify real lazy-module imports and language/diagram behavior before treating this path as passing.

The normal build runner must typecheck with `--noEmit` (768 MiB heap), then run Vite (1536 MiB heap), never concurrently. On Linux with a user systemd manager, automatically isolate only that invocation in its own bounded unit; do not change the Executor unit. Non-systemd platforms retain heap/concurrency limits and must explicitly report that these are **not** a total-memory cap. `KALA_BUILD_SYSTEMD=required` must fail closed if the hard resource boundary is unavailable; `off` is for an already resource-limited CI/container. Forward environment variable names without secret values on command lines, and stop only the invocation-owned unit on cancellation. The build-owned unit sets `LimitCORE=0` so a heap failure cannot create a multi-gigabyte core dump.

## Verified checkpoint (2026-10-30)

The formal entrypoint completed typecheck, production Vite bundling and PWA generation with `KALA_BUILD_SYSTEMD=required KALA_BUILD_MEMORY_REPORT=1 node scripts/build.mjs`: exit 0/SUCCESS, service runtime 48.875 s, CPU 47.364 s, systemd-reported memory peak **2G** (rounded), swap **0B**. No budget was raised, unrelated service stopped, SDK/cache removed or in-use instance deployed. These numbers describe this workstation run, not a portable performance guarantee.

Real emitted lazy-module imports cover seven highlighting languages, language/theme registration and Mermaid flowchart/sequence parsing; five real Monaco workers compile and boot. A separate real Linux WebKit gate subsequently verified emitted Shiki TypeScript highlighting, Mermaid flowchart SVG layout and Monaco editor-Worker initialization RPC. This browser evidence is independent of build success; it does not claim every language editor interaction or arbitrary diagram/IdP compatibility. See the [native feature evidence](../architecture/desktop/application-debugging.md#9-implementation-and-acceptance-status).

The showcase recorder now invokes the same runner instead of its former 6 GiB Vite bypass. Main and prototype configurations both use the same native lazy-graph/Worker plugins. The CPU profile analyzer recursively reads nested maps and preserves relative paths to distinguish equal chunk basenames; actual analyzer fixtures verify nested/query URLs and actionable corrupt-map failure. Complete prototype and profiling runs must be reported separately, not inferred from the release build or plan assertions.

## Current open gate: full profiling build

A complete `KALA_PROFILE_SOURCEMAP=1` run reached chunk rendering but exhausted the **unchanged 1536 MiB Node heap**. It exited 1/FAILURE (service runtime 1 min 50.359 s, rounded unit peak 2G, swap 0B). Therefore full profiling is **not accepted** under this budget; native lazy/Worker map tests and recursive analyzer fixtures are narrower evidence, not a substitute. Keep this explicit gap rather than increasing the heap, changing production minification for profiling, or analyzing mismatched/stale maps. A further graph/render-memory reduction is needed.

The release was restored through the formal runner with `KALA_PROFILE_SOURCEMAP=0`: exit 0/SUCCESS, service runtime **59.718 s**, CPU 59.184 s, rounded peak **2G**, swap **0B**. A recursive check found no `.map` files in release output. The final locked native build/tests and real WebKit gate were then rerun against that restored production asset set and passed. Prototype uses the same reduction plugins but its full build is not included in this acceptance evidence.
