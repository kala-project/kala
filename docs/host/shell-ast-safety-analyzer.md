# Shell AST safety policy

**Status:** Source of Truth for `feat/shell-ast-safety`; review in progress, not a sandbox boundary.

## Contract

`analyzeShellCommand(command)` returns `safe`, `caution`, `high_risk` (explicit human approval), or `blocked` (never dispatch). Its **single implementation** lives in `packages/kernel/src/shell-safety.ts`; Host and Executor import/re-export it through their package dependency on `@agent-kernel/kernel`. This is a conservative policy heuristic, **not** a complete POSIX/Bash/PowerShell AST parser or a security isolation boundary.

The splitter examines top-level `&&`, `||`, `;`, `|`, `&`, and newlines; the analyzer recursively examines `$(...)`, backticks, parenthesized subshells, literal interpreter `-c` scripts, `env -S`, `find -exec`, and `xargs`. It checks privileged wrappers, destructive git/filesystem/process actions, network-to-shell pipes, device/system writes, `eval`, `${var@P}` and indirect expansion. Unclosed quotes/groups and recursion past eight levels are `blocked`. Opaque shell files/input, control-flow or function definitions, aliases, process substitution, here-documents, ANSI-C quoting, dynamic executable names, scripts assembled through command substitution, general-purpose interpreters, `find -exec`, `xargs`, BusyBox, git aliases/unknown subcommands/configuration/external diff, `rg --pre`, and `sed` script options are `high_risk`, not silently `caution`. `tee` targeting absolute paths, home-directory paths, parent traversal, or dynamic paths is likewise high-risk. Rule IDs and reasons are returned in `findings`. An unrecognized command is usually `caution`, not necessarily harmless.

## Authorization and replay

* `packages/kernel/src/handlers.ts`: `blocked` shell/bash calls produce a synthetic refusal and no tool effect. `high_risk` calls under `allow_all`, `auto`, or `ask` wait for approval; under `deny` they are rejected. Only `user_approve` sets `pendingCalls[].explicitlyApproved`, so `fold(initial, events, config)` reconstructs the same authorization bit from persisted events (JSONL and authority-backed sessions).
* `packages/host/src/loop.ts`: independently of optional extension registries, pre-dispatch refuses `blocked` calls and any `high_risk` call without a matching, dispatched, explicitly approved pending call (same call ID, tool name, and command). The builtin extension guard repeats this check. `request_approval` is auto-rejected for headless children rather than waiting forever.
* `packages/host/src/agent-runtime/copilot-runtime.ts`: Copilot tool callbacks evaluate the same policy; high-risk parent calls wait for approval; headless children and blocked calls are rejected. A Copilot approval projection records `explicitlyApproved` in session state.
* `packages/executor/src/client.ts` and `packages/host/src/connection/executor-ns.ts`: before journaling or running any `high_risk` shell/bash call, the Executor requests `executor:shell_authorize` over its authenticated Socket.IO connection. The Host refreshes the executor credential, looks up the session from its current store/authority, verifies workspace binding and a matching dispatched, explicitly approved call ID/name/command, and replies with a boolean. Timeout, disconnect, stale/missing approval, parse rejection, or unavailable authority deny admission. Safe/caution calls do not require a round trip, and duplicate completed receipts do not start a second execution. An older Host without the RPC will time out (fail closed for high-risk commands). The shell runner also rejects `high_risk` direct invocations unless the Executor transport supplied the verified approval context; `blocked` calls are rejected regardless of approval.

`blocked` is not overrideable by a tool input flag. A dynamic script that cannot be classified must not be silently treated as read-only. Tests: `packages/kernel/src/shell-safety.test.ts` checks reducer approval for opaque syntax; `packages/host/src/extensions/shell-ast-safety.test.ts` checks classifier identity with Kernel, valid obfuscations, SQLite-backed headless rejection, workspace/call-bound authorization, and host pre-dispatch; `packages/executor/src/tools/shell-ast-safety.test.ts` checks direct runner rejection and classifier identity; `packages/executor/src/client.idempotency.test.ts` covers remote denial/authorized dispatch and concurrent duplicate admission. `packages/host/src/store/postgres-session.integration.test.ts` adds an opt-in PostgreSQL approval test that deletes the latest projection to force event-stream replay. That integration suite requires `KALA_RUN_POSTGRES_INTEGRATION=1` and an available, preinstalled PostgreSQL test image.

## Known limitations / release gates

The lexer is not a full shell grammar: it escalates known unsupported constructs instead of trying to interpret them, but cannot prove completeness for nested quoting, arbitrary interpreters or shell command wrappers, aliases from external configuration, shell glob expansion, commands fetched from files/network, or PowerShell-specific syntax. A subprocess launched by an otherwise `caution` command (for example `npm run build`) is outside the visible command string; `caution` is **not** a guarantee that its side effects are safe. Executable-specific escape flags not in the rule catalog remain a gap. The classifier has no `cwd` or `workspaceRoot` input and does not reliably catch paths outside a workspace, all secret exfiltration, or all redirected writes. The online RPC authenticates the connected Host as the policy authority; it is **not** an offline signed proof against a malicious/compromised Host or someone with code execution on the Executor machine. Mixed-version Executors predating this guard must be upgraded before relying on remote admission. Complete grammar coverage or a sandbox/allowlisted execution model is required before representing this policy as protection against an adversarial shell payload; retain the executor sandbox and restrict direct executor access.
