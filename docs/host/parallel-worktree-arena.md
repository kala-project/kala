# Parallel Worktree Arena (`worktree_arena`) — Source-of-Truth Design

**Status:** EXPERIMENTAL, merged locally but **not production-deployed**. PG named operations have durable effect and canonical-repository claim barriers; Portable Bash retains its original cross-generation hazard. UNKNOWN effects without trustworthy final-effect evidence remain fenced; merging does not authorize an upgrade of the legacy Dedicated deployment.
**Scope:** `packages/host` Arena tool and PG effect ownership; `packages/executor` named `arena_git_probe` / `arena_git_status` / `arena_git_diff` / `arena_git_init` / `arena_git_apply` / `arena_git_cleanup` primitives.
**Deployment Coverage:** Local named Git mutations, real PostgreSQL two-replica races, surviving Git after Executor SIGKILL/PG restart, and Linux-only reconciliation using a dedicated PG LOGIN and persisted Session authority metadata. The bounded `init` repair restores a verified complete Git worktree into replayable Session metadata **without clearing UNKNOWN**. Production Dedicated operator provisioning, same-PID-namespace access and `apply`/partial-`cleanup` repair remain unproven.

---

## 1. Problem Statement & Motivation

When an Agent explores competing implementations, refactors, or bug fixes in parallel (e.g., via sub-agents), running multiple agents in the same working directory causes immediate file-edit collisions, git index lock contention (`.git/index.lock`), and interleaved test runs.

The **Parallel Worktree Arena (`worktree_arena`)** provides first-class Git worktree lifecycle orchestration so an Agent can:
1. **Provision (`init`)** 1 to 6 isolated Git worktrees (`<repoRoot>/.kala-arena/<arenaId>/<candidateId>`) on dedicated branches (`kala-arena/<arenaId>/<candidateId>`) from a common base commit (`HEAD` or custom `base_ref`).
2. **Inspect (`status` / `diff`)** live status, file modification counts, diff stats, and bounded unified diffs across all candidates side by side.
3. **Promote (`apply`)** the winning candidate's committed and/or uncommitted changes cleanly back into the primary workspace (`merge` or `patch`).
4. **Teardown (`cleanup`)** candidate worktrees and temporary arena branches without leaving orphaned Git metadata or untracked artifacts.

## 2. Multi-Deployment Architecture

```
┌──────────────────────────────────────────────────────────────────────────┐
│ Host (`packages/host/src/extensions/worktree-arena.ts`)                  │
│  1. Owner Lease Check: capture generation at entry; check before/after  │
│     each Executor call and durable metadata write                        │
│  2. State Recovery: `deps.store.findLatestRuntimeMetadata(sessionId,     │
│     'worktree_arena.state')` (JSONL / SQLite / PostgreSQL authority)     │
│  3. Portable Bash / PG named Git tools via the Session's Executor        │
│  4. Durable State Commit: `deps.store.appendRuntimeMetadata(sessionId,   │
│     { action: 'worktree_arena.state', payload }, { durable: true })`     │
└────────────────────────────────────┬─────────────────────────────────────┘
                                     │ ToolDispatcher (Portable Bash / PG named Git)
                                     ▼
┌──────────────────────────────────────────────────────────────────────────┐
│ Executor Workspace (`<repoRoot>`)                                        │
│  - `.git/info/exclude` -> `.kala-arena/` (keeps main `git status` clean) │
│  - `.kala-arena/<arenaId>/<candidateId>/` (inside Sandbox root so        │
│    sub-agents can use `read_file`, `write_file`, `replace_in_file`,      │
│    and `shell` without `EACCES: path outside workspace`)                 │
└──────────────────────────────────────────────────────────────────────────┘
```

### 2.1 Why Worktrees Live Under `<repoRoot>/.kala-arena/`

- **Executor Sandbox Compatibility**: Kala's Executor enforces `ctx.sandbox.resolve(path)` against the workspace roots. Placing worktrees in `/tmp` would cause `read_file`, `write_file`, `replace_in_file`, and `shell(cwd=...)` to fail with `EACCES`. Placing them under `<repoRoot>/.kala-arena/<arenaId>/<candidateId>` keeps every candidate inside the authorized workspace root.
- **Zero Main-Worktree Pollution**: During `init`, `worktree_arena` ensures `.kala-arena/` is listed in `<gitCommonDir>/info/exclude`, so `git status` in the primary workspace never reports `.kala-arena/` as untracked and `.gitignore` is never dirtied.

### 2.2 Deployment Mode Invariants

| Deployment Mode | How `worktree_arena` Operates |
|---|---|
| **Portable Mode** | Executes Git commands through a Host-only `callArenaShell` channel against the local Executor and persists `worktree_arena.state` in the Session JSONL log (`runtime_metadata`). Requires a dispatched `worktree_arena` parent with matching input and **explicit** approval. The Host registers each synthetic Bash call's exact command/workspace against that parent; the Executor's Shell AST high-risk authorization round trip verifies the registration and still rejects blocked commands. Missing approval or authorization fails closed. Portable mode still lacks PG effect isolation and is not safe for cross-generation mutation. |
| **Dedicated Mode** | Host and Executor run in separate containers/hosts without a shared filesystem. `worktree_arena` never touches the Host's local `fs`; all Git worktree operations execute on the remote Executor via `deps.tools.callTool`. |
| **Private Cloud Mode — EXPERIMENTAL, NOT MERGE-READY** | `probe` reads the canonical Git common-directory device/inode; PG claims that repository globally across workspace IDs, tenants and Sessions until final cleanup. Named actions register a durable PG effect before Host dispatch. Generation-bound Executor receipts and durable Host state precede effect completion. Unknown outcomes block owner handoff indefinitely. The old Bash mutation path remains Portable-only. |

### 2.2.1 Blocking final-effect race

1. Replica A checks generation G1 and dispatches a Bash command; the Executor admits the call under G1 and starts the shell.
2. The owner lease transfers to replica B (G2). A's already admitted shell continues and can run `git worktree add`, `git merge`, `git apply`, or `git worktree remove` **after** G2 becomes authoritative.
3. A's post-call `assertOwner` rejects its result but cannot undo the mutation. B may concurrently run a command on the same repository. The receipt journal deduplicates a *call ID*, not different calls from two generations. Re-dispatch of a pending call can wait on the old in-flight runner. `tool:cancel` is a best-effort abort message and is not an ownership-transfer barrier, nor does it roll back Git changes.

The local-Executor regression in `worktree-arena.test.ts` reproduces this ordering: after generation changes, a previously admitted shell creates a worktree and the Host rejects its result. **This feature must not be merged as multi-replica safe.** A fix needs an authoritative, generation-scoped Executor-side admission/revocation protocol and a serialized barrier covering the final filesystem mutation and owner handoff; old-generation shell termination/confirmation must precede new-generation effects. A real two-replica remote Executor failover test must prove that no G1 Git effect can execute after G2 takes ownership, including disconnects and redispatch, before changing this status.

**Feasibility investigation:** A per-session mutex held only by the Executor until Bash exits would serialize G1 and G2 *commands*, but would **not** prevent the PostgreSQL owner lease from expiring and G2 being acquired while G1 Bash still runs. PG active-effect rows do prevent takeover of **registered** effects, including after expiry. Legacy Bash actions are not used in PG mode. The Host's owner assertions are short database transactions, not locks held across `runOne`. Executor receipts deduplicate a call ID, but do not by themselves serialize different generations; that is the PG effect row's job.

**Required protocol before integration:** Couple an authoritative per-session *and per-repository* exclusive effect guard to Session ownership acquisition, renewal, release and takeover; G2 must be unable to become authoritative while a G1 Git effect can still execute. Authenticate the Executor's generation and tenant/workspace identity against that guard; serialize commands across Executor sockets and all sessions touching the same repository; bind each receipt to the exact generation. A takeover needs durable proof the previous effect has exited **and all its children can no longer mutate** before advancing the generation. On Host disconnect, timeout, membership loss, or Executor crash, do not release the guard merely because the Host lease or Executor connection expires: drain/terminate and reap the entire subprocess tree (including escaped descendants), or fail closed until an operator reconciles the Git state. An ordinary PostgreSQL advisory lock held by the Executor would release on Executor death even if an orphaned child continues, so it alone is insufficient. Neither current Host ownership APIs nor Executor sandbox/process lifetime management supplies this barrier. End-to-end tests must cover handoff with Bash blocked immediately before each Git mutation, Host crash/reconnect, Executor crash and surviving child, lost acknowledgement/replay, and different Sessions sharing one repository. Until such tests pass, **do not claim a final-effect fence or merge this feature as multi-replica ready**.

**PostgreSQL barrier (migrations 12–14, tightened in v27):** `registerWorkspaceEffect` locks the exact Session generation's owner row and records a workspace-wide effect (unique `workspace_id`) and, after an approved bounded `arena_git_probe`, a repository-scoped effect (unique `repository_identity`). The probe derives `git-common-inode:<device>:<inode>` from the canonical Git common directory inside the Executor sandbox. A separate globally unique repository claim names its exact organization, Unit, Session and arena ID; other tenants/Sessions cannot mutate that repository even *between* Git calls. A final verified cleanup now releases the claim **and** completes its effect in one owner-fenced transaction. `acquireResourceOwner` and `releaseResourceOwner` refuse handoff/release with unresolved effects, including after expiry or membership loss. Completion requires the original generation/token even after expiry; no TTL clears effects or claims. Symlink aliases and different workspace IDs sharing the same physical Git common directory serialize; separately mounted filesystems with indistinguishable device/inode pairs conservatively collide. Bind mounts that expose the *same* device/inode remain serialized.

**Still required before merge/deployment:** The Linux operator command uses a dedicated, organization-bound PG LOGIN and reads durable `worktree_arena.state` from PG after restart; no state JSON input or owner URL is accepted. SECURITY DEFINER functions atomically audit one repair or release and require an expired original owner, exact effect/generation and current Session metadata. A complete `init` intent can be repaired from observed Git worktrees while leaving the effect UNKNOWN for a second, separately confirmed reconciliation. Partial `init`, interrupted `apply` and partial `cleanup` remain blocked without a separately proved recovery procedure and original request details. Rehearse the real external Executor's original PID-namespace keeper, operator TLS/CA and workspace mounts before production use; the old Compose Runtime is **not** the Executor. Same-user Git-config changes between preflight and execution remain outside the threat model; malicious static config is rejected. Do not bypass parent Shell AST approval with synthetic Bash.

**Named Linux Executor path:** Each action requires its dispatched/approved `worktree_arena` parent. `probe` is itself receipt-journaled with a PG workspace effect; Host then verifies its repository identity before registering and dispatching a separate action-specific repository effect. `init` establishes claim and prepared effect atomically; other actions require the existing claim. The Executor independently rechecks Git common-directory identity. Its durable receipt journal, Host origin, matching owner generation and action-bound ID are mandatory. Fixed `/usr/bin/git` (never workspace `PATH`) uses bounded arguments and output; static executable-helper config is rejected. `diff` includes bounded regular untracked files without index writes. `init` records an initializing intent; `apply` records an applying intent, then the Host persists validated final state before effect completion. `cleanup` persists each candidate's cleaned state before its effect is cleared. `cleanup_after` is rejected in PG mode; use a separately approved cleanup call. A lost, failed, malformed, truncated or unknown outcome leaves its effect unresolved indefinitely. `inspectWorkspaceEffects(scope, 1..100)` and the authenticated internal `inspectArenaReceipt(sessionId, callId)` are **read-only**; a restarted Executor reports `started` for a missing final receipt. Pinned Arena journal entries are not evicted by ordinary TTL/capacity pruning; a full journal fails closed. Real PG tests exercise an admitted init stalled across expiry, cross-tenant same-repository claims, Executor SIGKILL, two Executor processes, PostgreSQL restart and UNKNOWN takeover blocking.

Portable synthetic high-risk `arena-*` Bash call IDs do not inherit approval automatically. Their Host-only registration requires the explicitly approved `worktree_arena` parent, and Executor Shell AST authorizes the exact synthetic call/command/workspace while the dispatch is outstanding. Blocked commands remain blocked. PG uses named non-Bash tools with explicit parent action authorization; neither route bypasses the Bash guard.

**Remaining operator boundary:** Linux process groups record Git and Executor PID, `/proc` start time, kernel boot ID **and PID namespace inode** before admission. The external Executor CLI now optionally consumes `arenaKeeperIdentityFile` in its protected managed config (or `--arena-keeper-file` for an explicit unmanaged run). Start `kala-executor arena-keeper <absolute-owner-only-identity-file>` as an **independent** service *before* admitting effects, in the same Linux PID namespace and under the same OS identity; use the separate unit's `flock` to serialize keeper starts. A private 0700 directory and atomically written 0600 identity file record keeper PID/start ticks/boot/PID namespace. Executor checks the live keeper on announcement and again before and after the durable admission record; Host refuses named Git dispatch unless the Executor advertises `arenaKeeperVersion: 1`. An absent, dead, wrong-namespace or self-referential keeper denies named actions, while ordinary old Executor tools remain available. On keeper loss after admission, the PG effect stays UNKNOWN, never auto-reconciled. The old Compose does not manage or automatically enroll the external Executor/keeper. The read-only `deploy/private-cloud/check-arena-executor-readiness.mjs` preflight **must** pass before an isolated rollout; it verifies the external config and keeper process, original workspace/journal path, owner-only CA/operator-file metadata, and unchanged legacy Compose topology **without reading either secret**; its output explicitly says `readyForProduction: false` because it cannot attest an externally operated Executor. An isolated loopback HTTPS/Socket.IO test generates its own self-signed CA, rejects an unrelated CA, runs a real child Executor and separate keeper in one Linux PID namespace, dispatches the named Git probe and status against a canonical temporary repository, rejects malicious static Git helper configuration, unapproved parent calls, an outside-sandbox path and a dead keeper, and verifies recovery after keeper restart. An independent keeper SIGKILL/restart plus a real orphaned Git child and PostgreSQL restart are separately covered by isolated integration tests. **Neither test proves the live production Executor's original workspace/journal mounts, TLS/CA handoff or production tenant authorization**; these need external evidence before use. Incomplete apply/cleanup recovery remains blocked; **not merge-ready**.

### 2.2.2 UNKNOWN / lost-ack operator runbook (bounded, fail-closed)

**Negative admission and lost ACK (experimental):** Each PG Arena effect is *prepared* with `dispatch_started=false` (combined migration 25; legacy Arena rows default to `true`). The registry commits a generation/owner-fenced one-way dispatch intent **before** its first remote frame; v26 also binds the canonical request digest to this PG transition. Capability/parent/socket refusals return a distinct local pre-dispatch failure. A rejected keeper check at Executor admission writes a separate **durable** generation/digest-bound `denied` receipt; Host reads it over the authenticated Executor channel and releases only for the matching request. A lost ACK for a completed read-only probe/status/diff may use the same read-only receipt query only when generation, canonical request digest, call ID and verified `finalEffectStopped` result match. Absent/unavailable/mismatched/started receipts never imply safety; no blind replay. A crash-stranded `dispatch_started=false` row can now be manually released by the org-scoped v26 operator: the PG lock rechecks the original expired generation, live Session and *never-started* marker, then writes an audit event and deletes the row atomically. A dispatched probe with no repository claim can be manually released **only** with the exact PG-bound digest and original *completed* receipt, stopped original Executor and all Git process groups, and current canonical repository/config proof. An original `started` receipt without final completion or lost journal is still UNKNOWN; even a stopped process does not assert an unrecorded final probe result. Keep it fenced rather than inventing a repository identity or treating receipt absence as negative admission. These are bounded paths, not general auto-recovery or production readiness.

**Isolated remote E2E:** The PostgreSQL multi-replica suite also dispatches a real named probe to a separate Socket.IO Executor with its original independent keeper, suppresses the actual Socket.IO ACK *after* the Executor commits its own `ExecutionReceiptStore` completion, SIGKILLs that Executor, checks the original journal/digest and runs the organization-limited operator CLI in the original PID namespace. PG audits the release; the previously blocked successor then acquires the Session. A second real remote probe pauses its Git worker immediately before launching `/usr/bin/git` (a deterministic test-only fault), records `started` and its process identity, then SIGKILLs the Executor; the surviving worker could still launch Git, so the operator refuses and the second PG replica cannot take over. The separate real `worktree add` fault test observes an **actual stopped Git child** surviving Executor SIGKILL and PostgreSQL restart and keeps its mutation UNKNOWN until independent process/repository verification. None of these tests manufactures a completed receipt as acceptance evidence; they do not prove any production keeper, TLS/CA handoff, workspace mount or production database history.

**v27 crash-window repair (not an automatic UNKNOWN release):** A named `init` now commits the repository claim **and its prepared, generation-bound effect in one PG transaction**, before persisting `initializing` metadata; a failed effect insert rolls back the claim. A crash before intent leaves claim+effect and prior Session metadata, never a new bare claim; a crash after intent leaves claim+effect+intent, never bare `initializing` metadata. The scoped operator's `--prepared` path locks the expired original generation, proves `dispatch_started=false`, checks the live Session and exact claim, and in **one transaction** audits/removes the effect and claim. If `initializing` was persisted, that same transaction restores the prior `cleaned` metadata or an absent Arena state through the durable hot-event projection. A changed state, claim, owner, or dispatch marker rolls everything back. No Git admission can occur before the Host commits the dispatch marker. A *historical* v26 claim **without any effect** lacks this durable never-dispatched proof; do not infer safety from missing rows or force-release it. It remains blocked pending a separately reviewed offline compatibility process. Final verified cleanup now commits claim deletion and effect completion under one owner/generation fence; a failed delete rolls back both. A historical old two-transaction gap (`cleanup` effect present but claim already absent) can be audited through the same org operator after original journal/process, canonical Git cleanup and Session state checks: its scoped read reports the absent claim, and the definer routine requires explicit `claimMissing=true` evidence and **no other tenant's claim for that repository**. It refuses forged absence, changed generation and any live replacement claim. Isolated PG tests exercise insert rollback, both init crash boundaries, G2 fencing, atomic cleanup commit/rollback and restricted legacy reconciliation; the legacy cleanup CLI with an actual original remote receipt still needs a dedicated end-to-end rehearsal before production.

**Migration compatibility plan (local main Board integration):** Board migrations 12–18 retain their exact prior names, SQL and checksums; Arena's previously private migrations 12–18 are now appended as 19–25 without changing their SQL payload; v26 adds the operator dispatch/digest proof and v27 addresses the two claim/effect crash windows. Fresh isolated PostgreSQL tests apply v11→v27 and confirm both Board and Arena tables, intact v1–v11 checksums and Board v17→v18 backfill. This **is not an automatic upgrade** for databases that privately applied Arena v12–v18: their version 12 already names `active_workspace_effect_barrier`, not Board's `session_tree_agent_boards`. The schema verifier deliberately rejects such histories before DDL with an explicit identity-conflict warning; do not rewrite history rows, renumber in place, or run this merged release against them. Preserve a consistent backup and original schema/receipt journals, freeze all writers, and perform a separately reviewed offline data migration into a **fresh** v27 schema only after field-level Board/Arena state mapping and tenant/receipt identity checks have dedicated tests. No conversion tool or production rehearsal exists here; those instances remain blocked, not automatically repaired. The v1–v18 migration definition block is byte-identical to local main, but isolated v11→v27 tests cannot prove the identity of **actual production database rows** without a separately authorized read-only inspection; no production DB was contacted. Old images reject v27.

### 2.3 Safety Boundaries and Recovery

- An `arena_id` must be unique in the workspace: existing arena directories, symlinked arena paths, branches, and symlinked Git exclude paths cause initialization to fail. The tool does not overwrite or implicitly clean another arena. An existing session arena must be explicitly cleaned before another `init`.
- In PG mode, the durable repository claim **and prepared init effect** are committed atomically before the `initializing` intent, which is committed before Executor filesystem admission. Portable mode records each successful candidate; PG mode persists the Executor's validated final candidate set only after its complete receipt. If an Executor response is lost, inspect the receipt, process tree, arena directory and Git worktree registrations before cleanup/retry. Do not retry `init` blindly. Cleanup verifies recorded path/branch identity and never falls back to `rm -rf`; an unknown artifact blocks cleanup for manual inspection.
- `apply` requires a clean primary worktree whose `HEAD` equals `baseSha`, and an intact candidate branch derived from that base. `merge` commits candidate changes and uses `--ff-only` rather than risking a conflicted merge. `patch` checks a binary diff before applying it to the primary index; no temporary patch file is written. Applying a second time is rejected. External concurrent edits to Git/worktrees during a command are outside the tool's guarantees; use one authorized session owner and avoid competing mutations on the same repo.
- If an Executor acknowledgement is lost **after** a Git effect but **before** its durable state record, neither replay nor a resumed Host can automatically prove whether `apply` completed. The clean-base precondition blocks an accidental repeated merge/patch, but an operator must inspect `HEAD`, index, worktrees, and latest arena metadata to reconcile the outcome. Do not equate an unsuccessful tool response with rolled-back Git changes.
- `.git/info/exclude` is shared by Git worktrees and the `.kala-arena/` rule is retained after cleanup to avoid altering an existing user's ignore rules. It is not a per-session isolation boundary; Executor workspace authorization and session routing supply that boundary. The Host does not execute local Git commands, but shell commands on the Executor retain the underlying Executor's filesystem permissions.

## 3. Tool Schema & Operations

Tool name: `worktree_arena` (execution kind: `host`, risk: `write`, `requiresApproval: true`)

| Parameter | Type | Required | Description |
|---|---|---|---|
| `action` | `'init' \| 'status' \| 'diff' \| 'apply' \| 'cleanup'` | Yes | Arena lifecycle operation to run. |

| `base_ref` | `string` | No (`init`) | Git ref to branch candidates from (default `'HEAD'`). |

| `strategy` | `'merge' \| 'patch'` | No (`apply`) | How to apply the winning candidate to the primary worktree (default `'merge'`). |

| `stat_only` | `boolean` | No (`diff`) | Return only diff stats and changed files without full unified diff hunks. |
| `max_chars` | `integer (500..64000)` | No (`diff`) | Maximum characters of unified diff output per candidate (default `16000`). |

## 4. Verification & Acceptance Criteria

1. `init` creates isolated Git worktrees under `.kala-arena/<arenaId>/<candidateId>` on branches `kala-arena/<arenaId>/<candidateId>`, registers `.kala-arena/` in `.git/info/exclude`, and persists `worktree_arena.state`.
2. Independent edits in candidate worktrees (`candidate-a` vs `candidate-b`) do not collide and are accurately reported by `status` and `diff`.
3. `apply` promotes the selected candidate's changes (including uncommitted working-tree edits or commits) into a clean primary workspace at the arena base via fast-forward `merge` or checked `patch`.
4. `cleanup` removes the Git worktrees and temporary branches cleanly.
5. State survives across Host instances sharing a `SqliteSessionAuthority`, but Portable Bash checks at command and metadata boundaries are insufficient to prevent in-flight cross-generation mutation. PostgreSQL tests exercise real-path alias claims across tenants/Sessions and races across two replicas. A real `git worktree add` child survives network-connected Executor SIGKILL, later writes a worktree file, and remains UNKNOWN after PG and second Executor restart; reconciliation is rejected while Git runs and when exported Arena state disagrees, then audited when process and Git state agree.
