# Closed-Loop Skill & Memory Self-Learning (`skill_manager`, Learning Nudge, & Autonomous Skill Extraction)

**Status**: Experimental, locally integrated but not production-deployed. Owner-fenced `skill_manager` create/patch/delete and generic bound-Executor workspace memory writes use the Arena PostgreSQL active-workspace-effect barrier and exact durable completion receipts. Owner-fenced manual consolidation and at-most-once PostgreSQL-claimed background extraction are enabled on a bound Linux workspace. Interrupted extraction attempts are not retried. Host-local background extraction remains at-most-once; this is not an exactly-once self-learning workflow.
**Scope**: `packages/host/src/extensions/skill-manager.ts`, `packages/host/src/extensions/memory-consolidation.ts`, `packages/host/src/extensions/skills.ts`, `packages/host/src/builtin-tools.ts`, `packages/host/src/extensions/builtin-registry.ts`
**References**: `references/hermes-agent/tools/skill_manager_tool.py`, `references/hermes-agent/agent/memory_manager.py`, `references/claude-code-collection/memory/consolidator.py`

**Current support matrix**:

| Scope | Linux | macOS | Windows |
| --- | --- | --- | --- |
| Workspace discovery and load | Executor-backed | Executor-backed | Executor-backed |
| Workspace create, patch, delete without shared Owner fencing | Executor-bound | Executor-bound | Executor-bound |
| Executor-bound manual consolidation without shared Owner fencing | Supported | Supported | Supported |
| Shared-owner `skill_manager` create/patch/delete | Linux keeper and durable final receipt required; UNKNOWN blocks transfer | Unavailable: Linux keeper required | Unavailable: Linux keeper required |
| Shared-owner workspace memory write/delete and manual consolidation | Linux keeper and durable final receipt required; UNKNOWN blocks transfer | Unavailable: Linux keeper required | Unavailable: Linux keeper required |
| Shared-owner Executor-bound background extraction | PostgreSQL claim; no retry after attempt | Unavailable: Linux keeper required | Unavailable: Linux keeper required |
| Non-Executor-bound Host-local background consolidation | At-most-once | At-most-once | At-most-once |
| Host-global mutations | Trusted Host-local root only | Trusted Host-local root only | Trusted Host-local root only |

Workspace skill mutations follow the same trust boundary as existing Executor file tools: the user trusts their own workspace and same-user concurrent path changes. The dedicated `skill_file` Executor tool resolves `.agent/skills/<name>/SKILL.md` relative to the session's Executor cwd, applies configured sandbox roots, creates exclusively, and requires a SHA-256 revision for replacement and deletion. It is not a security boundary against a malicious same-user process swapping intermediate directories. Shared-owner skill mutations register a **prepared** active workspace effect in PostgreSQL under the current owner generation before attempting the mutating Executor RPC. The Host commits a one-way dispatch marker with the exact request digest immediately before emitting the frame. The Executor advertises `skillFileEffectVersion: 2` only with a durable receipt journal and healthy independent Linux keeper, and accepts generation-bound skill mutations only with Host origin, matching generation, and a named call ID. The Host releases the effect only after verifying the Executor's persisted completed receipt matches the call, generation, request digest, and acknowledged result. `skill_file` uses awaited Node filesystem operations, not spawned processes: completion of `runOne` proves the tool has stopped issuing filesystem effects. The normal read step is not a write; patch/delete still require revision CAS. A pre-dispatch refusal releases only after PostgreSQL proves `dispatch_started = false`. Another replica cannot acquire or release the Session owner while an effect remains active, even after expiry.

### Implementation blockers and acceptance boundary

- `packages/host/src/extensions/skill-manager.ts` dispatches workspace create/patch/delete via `skill_file` to the bound Executor. The Host never reconstructs a Host filesystem path for this scope; `packages/host/src/extensions/skills.ts` discovers/loads from the same bound workspace. Revision mismatch fails rather than overwriting another writer. An old Executor without this tool cannot perform these actions.
- `packages/host/src/connection/executor.ts` commits the Skill dispatch intent against the registered effect and refuses old Executors without receipt support. The generic execution journal records the request digest and owner generation before execution and the result only after `skill_file` stops. Duplicate call IDs replay that receipt rather than executing again. Direct `skill_file` writes in a shared-owner session without a registered Skill effect are rejected by the Host; the Executor also rejects generation-bound mutations without the matching Host origin and ID.
- **UNKNOWN is deliberately sticky**: ACK loss, timeout, crash after a started receipt, missing/mismatched final receipt, or inability to prove non-dispatch leaves the PostgreSQL effect row and blocks lease transfer; no replay under a new ID and no automatic release. The dedicated tenant-scoped operator can release **only** a prepared Skill/memory effect whose PostgreSQL dispatch marker is still false with no digest, after the old lease expires and the Session remains live. `learning-effect-reconcile` uses an owner-only operator credential file and records an incident, original generation, workspace and operator identity in the same PostgreSQL transaction as the release. A stale generation, changed marker, another tenant, or a dispatched effect fails closed. The Host also labels socket authorization denial and stale bind **before dispatch** with a dedicated rejection, but releases only if PostgreSQL still proves `dispatch_started=false`.
- For read-only incident inspection, the existing dedicated, unprivileged Arena operator LOGIN (scoped to its own organization) can call `kala_arena_operator_effects(<org>, <unit>, <session>, 20)` and `kala_arena_operator_dispatch(<org>, <unit>, <session>, <effect-id>)`. `kala_operator_learning_jobs(<org>, <unit>, <session>, 20)` lists bounded background claims and attempt status without allowing retry or mutation. Use the existing `arena-effect-inspect` command to see effect markers; for an exact, never-dispatched `skill-file-<ULID>` or `memory-file-<sha256>` call `KALA_ARENA_RECONCILE_OPERATOR_URL_FILE=<0600-file> KALA_ARENA_OPERATOR_ID=<operator LOGIN> node dist/bin/learning-effect-reconcile.js <org> <unit> <session> <effect> <incident> verify-never-dispatched:<effect>` on Linux. Dispatched receipts, whether completed or started, **cannot be released by this procedure**. Never use administrator table DML or Arena reconciliation to bypass this stop.
- **Completed-only operator recovery for v2**: `learning-effect-reconcile-completed` on Linux takes the exact tenant/session/effect, canonical workspace root and target, original owner-only Executor journal, live independent keeper identity, and incident ID. It refuses a live Executor, a started/missing/mismatched receipt, non-builtin tool, changed original journal, foreign PID namespace, or a target whose canonical path digest, bounded final content hash, Skill status or memory tombstone disagrees with the original completed receipt. It never interprets a failed `result.ok` as successful. The tenant-scoped PostgreSQL function locks the original owner/effect, checks the old lease has expired, session is live, generation/workspace/dispatch digest unchanged, and atomically audits evidence before removing that one effect. An exact durable completed receipt plus current final state is not evidence that a different concurrent same-user writer cannot later change the file; that is the approved trusted-same-user-workspace model. Legacy v1 receipts lacked process identity/target digests and remain permanently UNKNOWN. **Started-only/missing receipts remain UNKNOWN**, even if the Executor exited or the target looks correct; no timeout or operator-supplied assertion replaces a durable completion.
- Invoke only with the dedicated tenant operator LOGIN: `KALA_ARENA_RECONCILE_OPERATOR_URL_FILE=<0600-file> KALA_ARENA_OPERATOR_ID=<operator LOGIN> node dist/bin/learning-effect-reconcile-completed.js <org> <unit> <session> <effect> <canonical-workspace-root> <canonical-target-path> <original-journal> <original-keeper-file> <incident> verify-stopped:<effect>`. The command prints only the effect ID and incident ID; detailed digests/process identities stay in the tenant-scoped PostgreSQL audit row. Run from the original Executor PID namespace; a different host, boot or namespace is not proof of process death.
- An invalid workspace target, missing content, or unavailable keeper **after the PostgreSQL dispatch marker** is not a prepared refusal. Before any tool runs, the Executor attempts a generation/digest-bound durable `learning_not_admitted` receipt; if that persistence fails, the effect stays UNKNOWN. The Host never treats a negative receipt as a completed mutation. After the old lease expires, the same tenant operator can audit/release **only** the exact original negative receipt with the command above and `verify-never-admitted:<effect>` instead of `verify-stopped:<effect>`; no process/target result is claimed, and a started/missing/mismatched receipt cannot use this path.
- The scoped PostgreSQL operator LOGIN is a **trusted incident-response credential**, not a tenant/application API: SQL cannot independently inspect `/proc` or the original workspace. Restrict its credential file and execution to the verified operator command/approved operator, never grant it to a caller that can supply arbitrary evidence JSON. A compromised operator or substituted original journal is outside this proof boundary. Completed and denied original learning receipts move to owner-only immutable per-effect archive files, then to separately fsynced per-effect verified index entries. The bounded live journal keeps only started/unarchived receipts and a constant-size index-count anchor: ordinary tool commits neither enumerate archived entries nor rewrite 500+ archive pointers. For a never-admitted learning call with no preceding started entry, Executor **first fsyncs its exact negative receipt in the live journal**, then publishes the archive and index before removing that live entry. Startup can recover an archive published before its index **only if the original journal still contains the identical negative receipt**. An orphaned archive with no such original entry, or one conflicting with a started/completed journal (even with matching generation/digest), fails closed; neither Executor nor operator may use it as proof of non-dispatch. Restore verified evidence for older orphan archives rather than inventing a denial. If the journal itself is missing, startup fails closed rather than guessing that no earlier started calls existed. Missing/mismatched index or archive fails closed. Duplicate call IDs still replay the original durable result; no missing archive ever authorizes rerunning an effect.
- **Disk capacity and offline recovery**: set `KALA_LEARNING_ARCHIVE_MAX_BYTES` on the original Executor to an integer ≥65536 (default 1 GiB). `node dist/bin/learning-receipt-archive.js status <original-journal>` reports indexed/retired counts, active archive bytes, limit and `atCapacity`. Alert well before 80% of the limit and monitor free space on **both** workspace and offline volumes; admission reserves 32 KiB. At the configured cap a new learning call receives a durable, generation-bound **never-admitted** receipt when possible; ordinary tools remain available. If even the live 500-entry journal cannot persist this proof, the effect stays UNKNOWN, never auto-releases, and the operator must restore storage/evidence. An unexpectedly oversized completion stays in the live journal rather than losing its recovery evidence and sets `atCapacity` across restarts; provision more verified space and raise the configured limit before admitting further learning. Keep journal, `.learning-index`, `.learning-archive`, and keeper identity together in backup/restore; do not delete any component or truncate an index to reclaim space.
- After a matching PostgreSQL effect was **actually finalized** (normal verified Host release or audited operator resolution), migration v32 stores its exact tenant/session/effect/generation/workspace/request digest in the same delete transaction. With the original Executor stopped and an independent keeper still alive, a dedicated tenant operator may move one matching original completed receipt to a separate, owner-only mounted offline filesystem using `KALA_ARENA_RECONCILE_OPERATOR_URL_FILE=<0600-file> KALA_ARENA_OPERATOR_ID=<operator LOGIN> node dist/bin/learning-receipt-archive.js retire <org> <unit> <session> <effect> <original-journal> <original-keeper-file> <offline-directory> <incident> verify-finalized:<effect>`. The command verifies exact scoped PG finalization, original archived digest and stopped process/groups before copying and fsyncing the cold receipt, then durably replaces its local index with a permanent replay-blocking tombstone **before** removing the online content. A crash after the tombstone but before unlink can be retried with the same cold copy; duplicate calls return UNKNOWN, **never execute again**. Missing finalization, started-only or legacy process-less completed receipts cannot be retired. A lost offline volume must be restored from backup for incident review; the local tombstone continues to block execution. Offline content can be checked against the index's retained SHA-256 digest; no memory plaintext is copied into these receipts.
- **Availability boundary**: periodically check a cold copy with `node dist/bin/learning-receipt-archive.js verify <original-journal> <offline-directory> <session> <effect>`; mismatch or missing media must be repaired from backup, never replaced with an unverified receipt. The online index retains one small tombstone per finalized call ID forever. Exact replay fencing for an unbounded set of historical IDs cannot use literally finite storage without a separately proven epoch/ID-retirement protocol. Archive contents have a configurable cap and an authenticated offline recovery path, but index entries still grow linearly; monitor `indexed` and disk capacity, allocate/restore storage before the index volume fills, and do not silently discard tombstones. Historical effects finalized before schema v32 have no durable PostgreSQL finalization proof and cannot use offline retirement; retain them and plan capacity accordingly. The isolated Linux PG integration runs the actual scoped `retire` CLI against a project-local mounted tmpfs with `KALA_RUN_LEARNING_ARCHIVE_MOUNT_E2E=1` (requires non-interactive `sudo mount/umount`); it also checks missing finalization, wrong tenant, living process, damaged cold copy and retry after tombstone publication.
- `packages/host/src/connection/executor.ts` also registers generic `memory` workspace write/delete effects immediately before dispatch; deterministic effect IDs bind the Session and original call ID. The same PostgreSQL barrier coordinates lease transfer, dispatch intent, and final durable Executor receipt. Shared-owner Skill/memory mutations now require Executor effect capability **v2** plus a healthy independent Linux PID-namespace keeper; old v1/keeper-less Executors are rejected before the PostgreSQL dispatch marker. Only the exact built-in tool implementations advertise v2; their original journal target metadata carries `builtin-v2`, so a same-named custom tool cannot be mistaken for a proven no-subprocess implementation. The Executor persists its Linux process identity together with generation, original request digest and SHA-256 digests of the resolved target path and write content (plus Skill expected revision when supplied) in the admission journal; it never duplicates memory content or plaintext target path there. `memory` uses awaited Node filesystem operations (including delete tombstones), not child processes. In shared-owner sessions, unprotected global Executor memory writes are refused; session memory is kernel state rather than workspace filesystem. A started or uncertain memory effect remains UNKNOWN.
- The generic Executor transport computes the same canonical request digest for Arena, Skill and memory through one `beginWorkspaceDispatch` admission helper; PostgreSQL commits the corresponding one-way marker before any frame. Skill policy, candidate validation and effect registration remain in the Host extension, not Kernel's pure FSM. The registry still must enforce the registered Skill call ID, updated Executor capability, bound owner generation and Host origin; generic workspace memory dispatch must register its effect and verify the final receipt before release. These transport guards are not optional extension decisions.
- Arena repository claim/init scans still reject legacy or Arena UNKNOWN effects with no repository identity, as well as an UNKNOWN effect bound to that exact repository. Exact named `skill-file-<ULID>` and `memory-file-<sha256>` rows have no repository identity by design; they block only their own Session owner transfer, **not** unrelated Arena repository claims across tenants. Malformed or legacy anonymous rows remain fail-closed in the repository scan.
- `packages/host/src/extensions/memory-consolidation.ts` allows manual extraction for Executor-bound workspaces with a bound cwd and a configured shared-Owner memory effect barrier. The generic Executor memory tool selects the sandbox root containing that cwd, or the bound cwd when roots are absent; Host dispatch forwards that cwd. `packages/host/src/extensions/builtin-registry.ts` schedules eligible background extraction. Host-local `background-learning.ts` persists one SHA-256 transcript-keyed checkpoint per run and the periodic nudge cadence next to the session log. Shared-owner jobs instead persist a PostgreSQL pending claim keyed by the Session and transcript fingerprint. A single owner generation atomically moves the claim to `attempted` **before** extraction; pending claims resume on session load across replicas. An attempted job is **never retried** after crash or takeover. Extraction may result in multiple independently fenced Executor Skill/memory effects; a checkpoint is not a global atomic commit of them. A stopped/uncertain effect remains UNKNOWN and blocks owner transfer. An attempted checkpoint without such an effect records interrupted extraction, not successful learning; review the tenant-scoped checkpoint listing, associated effect IDs and Executor logs rather than replaying automatically.
- Owner-fenced learning nudges are read-only and do not recommend workspace persistence. Non-owner-fenced Executor-bound sessions with a cwd may recommend workspace learning. Their periodic cadence remains process-local; only non-owner-fenced Hosts persist that counter. PostgreSQL-claimed jobs deduplicate across replicas but sacrifice automatic retries after attempt.
- On a non-owner-fenced Host, a rejected/throwing or indeterminate memory-tool dispatch terminates the current consolidation batch with an error instead of being silently counted as a skipped candidate. Explicitly unsuccessful tool results with a known outcome remain skipped candidates; neither case establishes final-effect fencing for the generic Executor memory tool.

PostgreSQL claim tests establish cross-replica deduplication of background attempts, not exactly-once completion of a whole extraction. Neither shared-owner nor Host-local at-most-once background extraction completes interrupted attempts automatically.

## 1. Problem Statement & Motivation

In baseline `kala`:
1. **Read-Only Skills**: The `skill` tool supports only `action: "list" | "load"`. Even when an Agent spends 15 turns diagnosing a subtle build quirk or discovering a multi-step deployment procedure, it has no first-class, security-validated tool to author a new `SKILL.md` or self-heal an outdated `SKILL.md` whose instructions broke after a repository refactor.
2. **Manual-Only Memory Consolidation**: `consolidateMemory` (`packages/host/src/extensions/memory-consolidation.ts`) only runs when the user manually invokes `/consolidate-memory` and only extracts flat memory notes—never procedural skills. Furthermore, during long or complex turns (`>= 8` tool calls or `>= 2` error-recovery cycles), the model receives no structured reminder to persist reusable procedural knowledge or durable facts before finishing.

---

## 2. Architecture & Design

We introduce a three-part closed-loop self-learning system:

1. **`skill_manager` Tool (`packages/host/src/extensions/skill-manager.ts`)**:
   - First-class host tool allowing the Agent to `create`, `patch`, or `delete` `SKILL.md` files in either `workspace` (`.agent/skills/<name>/SKILL.md`) or `global` (`~/.agent/skills/<name>/SKILL.md`) scope.
   - Enforces a deterministic **Skill Security & Structural Guard (`validateSkillContent`)** before any disk write.
   - Preserves **Prompt Cache Stability**: `skill` tool schema remains static (`action: "list" | "load"`), and `SkillManager.refreshSession(record)` updates the out-of-band session skill registry without mutating the historical system prompt prefix.

2. **Complexity & Periodic Learning Nudge (`evaluateLearningNudge` in `packages/host/src/extensions/memory-consolidation.ts`)**:
   - Tracks per-session turn metrics (`toolCallsInTurn`, `failedToolCallsInTurn`, `turnsSinceLastLearningReview`).
   - Evaluates whether a turn warrants a self-learning nudge:
     - **Complex turn trigger**: `toolCallsInTurn >= 8` (default), OR
     - **Error-recovery trigger**: `failedToolCallsInTurn >= 2` followed by successful tool execution, OR
     - **Periodic turn cadence**: `turnsSinceLastLearningReview >= 10`.
   - Injects a concise, non-intrusive ephemeral system reminder via `beforeModelCall` when a complex turn is wrapping up (or exposes `buildLearningNudgeMessage` for the model lifecycle), prompting the Agent to consider `skill_manager` (for reusable multi-step procedures) or `memory` (for durable user/project preferences).

3. **Unified Skill + Memory Consolidation (`consolidateMemory` enhancement in `packages/host/src/extensions/memory-consolidation.ts`)**:
   - Extends `ConsolidationOutcome` with `savedSkills: string[]`.
   - Enhances the consolidator output parser (`parseConsolidatorOutput`) and runner (`consolidateMemory`) so that in addition to `"memories": [...]`, the consolidator LLM can emit `"skills": [...]` (procedural workflows with `name`, `description`, `body`, `confidence`).
   - Validated skill candidates are written through `runSkillManagerTool` (`action: "create"`, without overwriting existing skills), subject to the same `validateSkillContent` guard. Host-local and PostgreSQL-claimed shared-owner sessions may extract in the background; interrupted attempts do not replay automatically.

## 3. Detailed Component Specifications

### 3.1 `skill_manager` Tool Schema & Operations

```ts
export type SkillManagerInput = {
  action: 'create' | 'patch' | 'delete'
  name: string              // /^[a-z0-9]+(-[a-z0-9]+)*$/ (max 64 chars)
  scope?: 'workspace' | 'global' // default: 'workspace'
  description?: string      // 1..1024 chars (required for create unless content has frontmatter)
  content?: string          // Full SKILL.md or markdown body for create
  old_string?: string       // Required for patch
  new_string?: string       // Required for patch
  replace_all?: boolean     // Optional for patch
  overwrite?: boolean       // Optional for create (default false)
}
```

- **`create`**:
  - Validates `name` against `/^[a-z0-9]+(-[a-z0-9]+)*$/` (`1..64` chars).
  - If `content` does not start with YAML frontmatter (`---`), synthesizes valid frontmatter from `name` and `description`.
  - Runs `validateSkillContent(name, fullMarkdown)`.
  - Checks if `<root>/<name>/SKILL.md` already exists; fails unless `overwrite === true`.
  - Workspace mutations use the bound Executor with exclusive create and revision-checked replacement; shared-owner writes require the registered PostgreSQL effect and exact durable Executor final receipt described above.
  - Trusted Host-global creates may explicitly request `overwrite: true`; consolidation never overwrites an existing skill. Workspace-bound sessions cannot mutate Host-global skills.
- **`patch`**:
  - Reads existing `<root>/<name>/SKILL.md`.
  - Performs exact `old_string` -> `new_string` replacement (rejecting missing or ambiguous `old_string` unless `replace_all === true`).
  - Runs `validateSkillContent(name, patchedMarkdown)` to ensure the patch did not corrupt frontmatter or introduce forbidden patterns.
  - Writes the updated content and refreshes `deps.skills`.
- **`delete`**:
  - Removes only `<root>/<name>/SKILL.md` (and `<root>/<name>` directory if empty), preserving sibling files, and refreshes `deps.skills`.

### 3.2 Skill Security & Structural Guard (`validateSkillContent`)

Every `create` and `patch` operation must pass `validateSkillContent(expectedName, rawContent)`:
1. **Size & Structure**:
   - Byte length `<= 256 * 1024` (256 KB) and non-empty body.
   - Valid YAML frontmatter (`--- ... ---`) with `name === expectedName` and `description` between `1` and `1024` characters.
2. **Security Pattern Scan**:
   - Rejects prompt-injection & instruction-hierarchy override phrases (e.g. `ignore previous instructions`, `ignore all prior instructions`, `disregard system prompt`, `system override`, `you are now in developer mode`).
   - Rejects credential exfiltration & covert network patterns (e.g. `curl ... $`, `wget ... $`, sending `.env` / `SSH_AUTH_SOCK` / `AWS_SECRET` / `OPENAI_API_KEY` / `ANTHROPIC_API_KEY` over network).
   - Rejects destructive host/root commands (`rm -rf /`, `mkfs.`, `:(){:|:&};:`).

Trusted Host-global skill mutations are limited to Host-local sessions: workspace-bound, organization-attributed and owner-fenced sessions cannot write this shared root, even when a test override supplies a path. They reject symlinked path components, but those checks are not a defense against concurrent path swaps: do not expose the Host-global root to workspace users. The security-pattern scan is defense-in-depth, not a guarantee that arbitrary prose is safe to follow. Non-owner-fenced consolidation checks any captured local activation before writes; owner-fenced consolidation is disabled. Global skill mutations check activation again immediately before asynchronous writes, but that is not an atomic final-effect fence.
The trusted-global child path check uses `dirname` rather than a hard-coded `/` separator so that Host-global writes also work on Windows.

### 3.3 Learning Nudge Tracker (`evaluateLearningNudge`)

- Maintained per session in `kala.memory` extension lifecycle hooks (`afterToolDispatch`, `beforeModelCall`, `afterTurn`):
  - `afterToolDispatch`: increments `toolCallsInTurn`; if `!result.ok`, increments `failedToolCallsInTurn`, else if `failedToolCallsInTurn > 0`, marks `recoveredFromFailure = true`.
  - `beforeModelCall`: when `evaluateLearningNudge(metrics)` returns `{ shouldNudge: true, reason }` and a nudge has not yet been injected in the current turn, appends a transient system-level learning reminder to the outgoing `messages` array (without mutating durable `record.state.messages` or the static system prompt prefix).
  - `afterTurn`: resets per-turn counters and increments `turnsSinceLastNudge` (or resets it if a nudge was delivered or `skill_manager` / `memory` write was called).

## 4. Verification & Acceptance Criteria

Skill and memory mutations, including shared-owner manual and PostgreSQL-claimed background consolidation, can be exercised on the bound Executor through PostgreSQL effect registration and final completion receipts. Background attempts have no automatic replay and cannot be equated with an atomic Skill/memory transaction.

1. **Skill Creation, Patching, & Discovery**:
   - `skill_manager { action: "create" }` writes a valid `.agent/skills/<name>/SKILL.md`, immediately discoverable via `skill { action: "list" }` and readable via `skill { action: "load", name }`.
   - `skill_manager { action: "patch" }` updates an existing skill (self-healing outdated instructions) and rejects patches that break frontmatter.
   - `skill_manager { action: "delete" }` removes the skill cleanly.
2. **Security Guard**:
   - `validateSkillContent` rejects prompt injection payloads, credential exfiltration commands, and malformed frontmatter.
3. **Learning Nudge & Autonomous Consolidation**:
   - `evaluateLearningNudge` triggers after `>= 8` tool calls, `>= 2` recovered tool failures, or `>= 10` turns, and suppresses duplicate nudges once `skill_manager` or `memory` write has been invoked in the turn.
   - `consolidateMemory` extracts both durable memories (`saved`) and procedural skills (`savedSkills`), validating skills through the same security guard.
